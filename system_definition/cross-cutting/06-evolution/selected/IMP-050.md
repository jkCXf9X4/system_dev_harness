# IMP-050: Remove Redundant Contract Fields After Planner-Orchestrator Consolidation

## Lifecycle Stage

Candidate

## Status

Proposed

## Layer

Evolution

## Theme

Remove agent output contract fields that became redundant when the planner absorbed the top-level orchestrator's routing and coordination role.

## Evidence

- `.opencode/agents/orchestrator-planner.md` lines 161-195: planner returns ~30 output fields, many of which are routing metadata that serves as the orchestrator's chain coordination — `route`, `issue_kind`, `requested_outcome`, `workflow_mode`, `handoff_required`, `large_job_triggered`, `plan_approval_status`, `plan_approval_reason`, `which downstream agents should be used next`, `whether this is a contained implementation task or a candidate-capture artifact persistence task`.
- `.opencode/agents/orchestrator-contract.md` line 32: contract agent returns `control flags from planning, corrected if discovery showed the planner was wrong` — a re-validation of planner-determined flags that the planner already resolved with its own discovery helper.
- `.opencode/dev_harness/workflow/plan-summary-schema.md`: plan summary file already contains `scope`, `files_touched`, `risk_assessment`, `candidate_linkages`, `large_job_triggered`, `plan_approval_status`, `plan_approval_reason`, `tailoring_record`. These are the authoritative fields.
- `orchestrator-planner.md` lines 152-159 "ID-Based Handoff": builder receives `task_id` + `plan_file_path` + compact work order scope. Remaining context is in the plan file. Yet the planner still returns 30 handoff fields to the orchestrator.
- `orchestrator` (alias) previously existed as a separate routing agent. The planner now directly handles all routing decisions: builder invocation, validation routing, reviewer routing, reflection routing, reporter invocation, user feedback pauses, revision loops, and clarification gates.

## Current Pain Or Risk

When the planner absorbed the top-level orchestrator role, it inherited the orchestrator's output contract alongside its own planning contract. This creates:

1. **Redundant routing fields**: `route: guarded_chain` is always the same value. `issue_kind` and `requested_outcome` are planner-internal classifications — builder and reviewer use `workflow_mode` (delivery/candidate_capture) as the action-significant field. These classification-only fields flow through the chain without being acted upon.

2. **Plan file duplication**: The plan summary file (`plan_file_path`) is the authoritative source for `scope`, `files_touched`, `risk_assessment`, `tailoring_record`, `large_job_triggered`, `plan_approval_status`, etc. But the planner also returns these same fields as handoff metadata — a second copy of the same information.

3. **Contract agent re-validation**: The contract agent's output includes `control flags from planning, corrected if discovery showed the planner was wrong`. Since the planner already invokes discovery as a directed helper, the contract agent's flag correction is a reconciliation step that should not be needed — the planner resolves flag uncertainty during planning.

4. **Field inflation**: The planner's output grew to accommodate both planning responsibilities (task definition, success criteria, traceability) and orchestrator responsibilities (routing, draft approval, handoff coordination). Now that both roles are unified in one agent, some fields serve only the orchestrator-to-orchestrator handoff (e.g., `which downstream agents should be used next`, `whether this is a contained implementation task or a candidate-capture artifact persistence task`).

5. **Token cost**: Each of these redundant fields adds static overhead to every planner output (~500-1000 tokens of routing metadata that either duplicates the plan file or is never acted upon by downstream stages).

## Proposed Improvement

Audit the planner's output contract and remove or down-scope fields that are redundant post-consolidation:

1. **Remove `route: guarded_chain`**: Always the same value. If the builder or reviewer needs to know the chain, they can reference `control-policy.md`.

2. **Down-scope `issue_kind` and `requested_outcome`**: These are planner-internal classification decisions. Move them into the plan summary file (already captured as scope context). Remove from the live handoff contract — downstream stages care about `workflow_mode`, not the classification taxonomy.

3. **Remove `handoff_required` and handoff notes**: This is an orchestrator coordination concern. If a handoff is needed, the planner routes it directly. The flag is informational duplication.

4. **Remove re-validation fields from contract agent**: Drop `control flags from planning, corrected if discovery showed the planner was wrong` from the contract agent's output contract. The planner owns flag correctness. If discovery was invoked during planning, the flags are already correct. If the contract agent disagrees, it should return the disagreement as an `improvement_candidate` or flag it for reviewer attention, not as a "correction" to planner output.

5. **Audit planner output fields against plan-file fields**: For every planner output field that also appears in the plan summary schema, ask: does a downstream stage actually need this as live handoff metadata, or can it load it from the plan file? Candidate removals: `large_job_triggered` (plan file has it), `plan_approval_status` (plan file has it), `plan_approval_reason` (plan file has it), `tailoring_record` (plan file has it), `risk triggers detected` (plan file has it via `tailoring_record`).

6. **Consolidate "next stage" guidance**: Replace `which downstream agents should be used next` and `whether this is a contained implementation task or a candidate-capture artifact persistence task` with a single `next_stage` field: `builder`, `none_until_clarified`, or `reporter` (for rejected/revision-cap-exceeded workflows). The builder already gets `workflow_mode` to distinguish delivery from candidate-capture.

7. **Keep fields genuinely needed by downstream stages**: `workflow_mode`, `task_id`, `plan_file_path`, control flags (`touches_information_artifacts`, `touches_product_breakdown`, `requires_decision_record`, `requires_external_research`, `touches_shared_interface`), success criteria, and the consolidated implementation work order. These are action-significant for the builder.

## Expected Benefit

- **Reduced planner output size**: Estimate 30-40% reduction in planner handoff token count by removing routing-only and plan-file-duplicated fields.
- **Single source of truth**: The plan summary file is the authoritative source for task metadata. Removes the ambiguity of "which copy is canonical?"
- **Cleaner contract separation**: Planner outputs planning decisions; routing decisions are implicit in the stage invocation order, not explicit in the contract.
- **Simpler contract agent**: Removes the "correct the planner" anti-pattern — the planner owns its flags, and contract agent focuses on requirement specification.
- **Easier maintenance**: Fewer fields to update when the planner's role changes, fewer synchronization points between handoff metadata and plan file.

## Risk And Blast Radius

Low to Medium — changes to planner output format only. No behavioral changes to routing, validation, or review. Specific risks:

- **Builder dependency**: The builder loads context from the plan file via `plan_file_path`. If a field is removed from the live handoff but the builder expects it, the builder must be updated to load it from the plan file. Mitigation: the builder already loads the plan file; verify all removed fields exist in `plan-summary-schema.md`.

- **Reviewer dependency**: The reviewer reads `plan_file_path` and verifies the plan file. If the reviewer previously relied on handoff metadata (e.g., `large_job_triggered`), ensure it loads those fields from the plan file instead.

- **Backward compatibility**: This is a planner output format change. No persisted data is affected. The plan file schema is the stable contract.

- **Affected files**: `orchestrator-planner.md` (output contract), `orchestrator-contract.md` (drop flag correction), `plan-summary-schema.md` (verify all needed fields are present). Possibly `orchestrator-builder.md` and `orchestrator-reviewer.md` if they reference removed fields directly.

## Task Contract Seed

Audit and trim the planner's output contract for post-consolidation redundancy:

1. Load `orchestrator-planner.md` output contract (lines 161-195) and `plan-summary-schema.md`.
2. For each planner output field, determine:
   - Is it also in the plan summary schema? If yes, can downstream stages load it from the plan file instead?
   - Is it routing metadata that exists because the orchestrator was previously a separate agent? If yes, is it still needed?
   - Is it acted upon by any downstream stage (builder, reviewer)? If no, remove it.
3. Remove fields identified as redundant: `route`, `handoff_required` and handoff notes.
4. Down-scope `issue_kind` and `requested_outcome`: move to plan summary schema or remove from live handoff.
5. Remove `large_job_triggered`, `plan_approval_status`, `plan_approval_reason`, `tailoring_record`, `risk triggers detected` from live handoff — these are in the plan file.
6. Consolidate `which downstream agents should be used next` and `whether this is a contained implementation task or a candidate-capture artifact persistence task` into a single `next_stage` field.
7. Keep: `task_id`, `plan_file_path`, `workflow_mode`, control flags, success criteria, implementation work order, common fields.
8. Update `orchestrator-contract.md`: drop `control flags from planning, corrected if discovery showed the planner was wrong`; replace with `control flags: as determined by planner work order`.
9. Verify builder and reviewer load needed fields from the plan file.

## Notes

This candidate is related to but distinct from IMP-044 (boilerplate reduction) and IMP-038 (prompt de-duplication). Those candidates address generic repetition of rules and fields across all agents. IMP-050 addresses a specific architectural redundancy: fields that exist because the planner and orchestrator were previously separate agents, and the consolidation left both sets of output fields in the unified planner.

The key principle: the plan summary file is the single authoritative source for task metadata. The live handoff from planner to builder should carry only fields that (a) are not in the plan file, or (b) are needed for immediate routing/action decisions before the plan file is loaded.
