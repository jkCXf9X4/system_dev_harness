## Current Pain Or Risk

The guarded chain moved from planner output to builder execution, with large jobs handled through `large_job_triggered` and `user_feedback_required`. This worked for larger jobs, but approval was implicit in a generic feedback pause. The workflow did not have a first-class draft plan state where the operator could approve, request revisions, or reject the work order before implementation began.

## Proposed Improvement

Add a lightweight planner-owned plan draft approval cycle before builder execution:

```text
planner -> plan_draft -> operator_decision -> builder
```

The planner emits a draft work order with compact approval state:

```text
plan_approval_status: not_required|pending
plan_approval_reason: large_job|destructive|operator_requested|not_applicable
```

For small routine tasks, the planner can set `plan_approval_status: not_required` and the orchestrator proceeds directly to builder. For large jobs, destructive work, high-blast-radius changes, or explicit plan-review requests, the planner sets `plan_approval_status: pending` and the orchestrator pauses before builder execution.

## Expected Benefit

Makes pre-execution approval explicit, reusable, and traceable. Large jobs become one trigger for draft approval instead of a separate control path. Operator decisions become stable workflow state, which improves auditability and reduces ambiguity around whether builder execution was authorized.

## Risk And Blast Radius

Medium. This changed planner output, orchestrator routing, reviewer expectations, large-job guidance, and plan archive fields. The design keeps small tasks lightweight through `plan_approval_status: not_required`.

## Task Contract Seed

Implemented in this coordinated pass:

1. Added `plan_approval_status` and `plan_approval_reason` to planner output for `workflow_mode: delivery`.
2. Defined approval triggers in `.opencode/dev_harness/workflow/control-policy.md`, including large jobs, destructive changes, and explicit user requests to review the plan before execution.
3. Updated `orchestrator.md` to route `pending` before calling builder and treat `approve`, `revise`, and `reject` as operator decisions.
4. Folded `large_job_triggered: true` into the draft approval cycle as one reason for `plan_approval_status: pending`.
5. Updated reviewer guidance to report missed required draft approval as a non-blocking process finding after implementation.
6. Updated plan archive fields for approval status traceability.

## Out Of Scope

- Adding a separate approval agent.
- Requiring operator approval for every small or low-risk task.
- Adding role-based access control or multi-person approval.
- Building a UI or external review system.
- Blocking completed implementation solely because draft approval was missed.
