# IMP-022: Declined — Verification Breakdown Structure (VBS) evaluated and architecturally ruled out

## Layer

Evolution (cross-cutting/06-evolution)

## Theme

Verification / INCOSE — Evaluation of a fourth decomposition tree (VBS) running parallel to FBS/PBS/WBS

## Evidence

- INCOSE SEHB v5.1 §2.3.4.1 — VBS not listed among prescribed breakdown structures (only FBS, PBS, WBS, OBS, CBS are defined)
- INCOSE SEHB v5.1 §1.3.5 — Verification belongs in the horizontal view at each element ("horizontal view includes... verification, or validation activities and results"), not extracted into a separate tree
- INCOSE SEHB v5.1 §2.3.5.9 — Verification is planned recursively per level as elements evolve, not decomposed as a standalone structure
- KM-004 (Minimize Parallel Structures) — adding a fourth decomposition tree duplicates existing mechanisms
- AD-004 precedent — SKILLS was declined for parallel structure duplication; same pattern applies to VBS

## Current Pain Or Risk

The VBS concept addresses a genuine desire for verification as a first-class structural concern, but creates more problems than it solves: structural redundancy with the existing PBS/FBS hierarchy, N-to-N traceability explosion between VBS and PBS elements, authority fragmentation (which file is authoritative for a given element's criteria?), and violation of INCOSE §1.3.5 horizontal-view co-location requirements.

## Proposed Improvement

Do not create a VBS. Instead, complete the IMP-021 per-layer verification.md pattern, which achieves all VBS goals (hierarchical decomposition, per-element criteria, cross-cutting consistency, formal traceability) through the INCOSE-consistent horizontal-view mechanism.

## Expected Benefit

Preserved INCOSE alignment, avoided structural over-engineering, no new decomposition tree to maintain, resolved (rather than compounded) verification authority model.

## Risk And Blast Radius

Low — this is a decline decision, not implementation work. The evaluation itself creates a candidate artifact only.

## Notes

This candidate records the complete VBS evaluation for future reference. It is not a rejection of verification improvement — it is a routing decision: the IMP-021 path is the INCOSE-consistent way to achieve the same goals without structural over-engineering. If the system grows significantly in verification complexity (e.g., 20+ layers, hundreds of criteria), the VBS question may warrant re-evaluation.

### Evaluation Summary

1. **INCOSE does not define a VBS.** The handbook lists five breakdown structures (FBS, PBS, WBS, OBS, CBS) and product, operations, evolution), cross-cutting consistency (centralized strategy document defines concerns every layer addresses), and formal traceability (per-layer cross-references to centralized criteria).

4. **Physical verification parallelism already exists.** The Reviewer agent architecture spawns parallel independent helpers (Verifier, Review: Architecture, Review: Completeness, Review: Lessons) that execute verification concurrently. This is the actual parallelism mechanism — not a static document structure.

5. **System scale is insufficient.** With ~5 verification layers and ~14 functions, the overhead of a fourth decomposition tree outweighs any benefit.

6. **KM-004 and AD-004 apply.** The project's established architecture preference for minimizing parallel structures and the SKILLS decline precedent both weigh against adding a VBS.

### Decision Log

An ED or AD entry documenting VBS non-adoption should be created to prevent future re-proposals without full architectural context.
