## Theme

PBS / Structure — Reify PBS as hierarchical tree with explicit SoI root, decomposable/atomic element annotations, and parent-child subordination relationships per INCOSE §1.3.5

## Evidence

- `system_definition/README.md` — Current PBS uses sequential numbered layers (00–06) rather than a partitioning hierarchy from a system-of-interest root.
- `system_definition/pbs/02-architecture/architecture.md` — Stable concepts and boundaries are described as a flat list, not as subordinate elements under a defined SoI.
- `system_definition/pbs/03-implementation/implementation.md` — Artifacts are listed in tables but not declared as atomic or decomposable elements of a parent system.
- `SE_V5/INCOSE_SEHB5.txt` lines 1512–1547 (§1.3.5 The Hierarchy within a System) — Defines PBS as "a partitioning of the system" with "distinct subsets of elements subordinated to a higher-level system." Describes atomic elements and span-of-control heuristic (7+/-2).
- `SE_V5/INCOSE_SEHB5.txt` lines 4747–4776 (§2.3.4.1 Breakdown Structures) — Describes PBS as "a breakdown of the SoI into successively lower-level details of its physical architecture."

## Current Pain Or Risk

- Sequential layers (00–06) obscure which artifacts decompose which parent elements. No reader can tell whether `04-verification` is a sibling or subordinate of `03-implementation`.
- No element declares atomic-vs-decomposable status, so make/buy/reuse decisions cannot be recorded per element.
- Span-of-control heuristic (7+/-2 per Urwick, 1956) is not applicable at lower levels because the hierarchy is not modeled as a tree.
- Traceability is linear (intent → product → architecture → implementation → verification) rather than tree-structured, making cross-element relationships harder to verify.

## Proposed Improvement

Restructure the PBS to start from an explicit SoI root `system_dev_harness` with subordinate elements (Planning, Implementation, Verification, Persistence, Evolution). Each branch decomposes until atomic leaves are reached. Each element declares:
- `element_type` (atomic|decomposable)
- `parent` reference
- `subordinates` list (for decomposable elements)

Maintain the existing numbered directory layout as a secondary organizational convenience, but add a `system_definition/product-tree.md` that captures the true hierarchical structure.

## Expected Benefit

- Readers can immediately see which artifacts are siblings, which are parent/child, and which are atomic leaves.
- Make/buy/reuse decisions become actionable once atomic elements are identified.
- Span-of-control heuristic can be validated at each decomposition level.
- Traceability links become tree-traversal paths rather than linear chains.

## Risk And Blast Radius
