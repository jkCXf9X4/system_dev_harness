## Evidence

- Every agent prompt repeats "If there is an obvious better or more correct answer..." (11 occurrences across agents)
- Every agent prompt repeats "Apply `.opencode/dev_harness/workflow/agent-boundaries.md`" (107 references across 20 agent files)
- Every agent prompt repeats "Apply `.opencode/dev_harness/workflow/subagent-lifecycle.md`" (45 references)
- Every agent prompt repeats "Apply `.opencode/dev_harness/workflow/stage-output-schema.md`" (62 references)
- Every agent prompt repeats "Do not modify files; use `.opencode/dev_harness/workflow/agent-boundaries.md`" (14 occurrences)
- `orchestrator` agent (150 lines) is a pure router — its only action is calling `orchestrator-planner`. It loads its full system prompt + conversation history per request, then routes to planner with no value-add logic.
- 16 of 20 agents define a `task:` permission block with `"*": deny` plus an explicit allow-list (repeated boilerplate per agent)
- Every planner output returns 40+ fields; for simple tasks ~30 are `none` or `not_applicable`
- Every helper lifecycle block includes `prior_context_dependency`, `context_rot_risk`, `handoff_summary` even when `reuse_decision` is `not_applicable`
- 14 workflow policy files under `.opencode/dev_harness/workflow/`, many <30 lines of actual rule content but each referenced in 5-15 agent prompts
- Agent output requirements list 10-20 return fields in prose, each with `"common fields from stage-output-schema.md"` appended (adding 5 more fields)
- Policy references in agent prompts use full file paths (`.opencode/dev_harness/workflow/interface-consistency.md`) 40+ characters each, repeated 200+ times across the system
- The `fresh_helper_handoff` format is 60+ lines of structured output repeated every time a new helper is invoked

## Current Pain Or Risk

The guarded orchestration workflow incurs substantial token overhead from three compounding sources:

1. **Instruction duplication.** Every agent loads a system prompt that repeats verbatim directives shared across all agents. For a simple task (single-line typo fix, metadata update), the overhead of loading 10+ agent instructions is 10-20× the actual work.

2. **Excessive stage count for trivial work.** A 1-line fix triggers: orchestrator → planner → discovery → contract → lessons → memory → builder → verifier → review-completeness → review-lessons → reviewer → reflection → reporter. Each stage consumes its full system prompt + handoff context even when it returns "no relevant findings." The `lightweight` profile exists but is not truly lightweight.

3. **Verbose inter-agent protocols.** Output schemas, helper lifecycle decisions, parallel helper plans, and structured handoffs add 500-2000 tokens per agent per task. For a task where total meaningful content is 100 tokens, the protocol overhead is 5-20×.

Token inefficiency directly reduces the effective context available for reasoning about the actual task. In long-running tasks with iterations, context-window pressure from protocol overhead increases the risk of agents losing track of the original task contract (KM-003).

## Proposed Improvement

Seven sub-optimizations, designed as independent delivery contracts so they can be scoped, implemented, and reviewed separately:

### OPT-01: Shared Common Policies File

Create `.opencode/dev_harness/workflow/_common-policies.md` containing all boilerplate directives shared across agents:

```text
# Common Policies

**Directives for all agents:**
1. If there is an obvious better or more correct answer than what was requested, flag this to the user before proceeding. Do not silently substitute your own judgment for the user's intent.
2. Apply `agent-boundaries.md` for read/write boundaries and scope containment.
3. Apply `stage-output-schema.md` for common output fields.
4. Apply `subagent-lifecycle.md` before sending follow-up work to an existing helper.
5. For system-definition work, apply `product-breakdown-work.md`.
6. For lessons/memory, apply `workflow-memory.md`.
7. Read-only agents: do not modify files using Edit or Write. Return blocking gaps, required follow-up, or `improvement_candidates` instead.
```

Replace every agent's repeated boilerplate block with a single line:

```text
Common policies: _common-policies.md
```

Estimated savings: ~300-600 tokens per agent per invocation × 10-15 agents = **~3000-9000 tokens per task**.

### OPT-02: Collapse Orchestrator Into Planner

- Move `orchestrator` routing rules into `orchestrator-planner` as a single "Route Selection" section.
- Make `orchestrator-planner` the primary entrypoint agent with `mode: primary`.
- Remove the `orchestrator` agent file entirely (or replace with a 5-line alias).
- The planner already knows the routing rules from `control-policy.md` (plan approval → builder, blocked → revision loop, approved → reflection → reporter). It dispatches to builder/reviewer/reporter via `task:` calls already.

Eliminates 150 lines of system prompt loading + full conversation review per task. Estimated savings: **~500-1000 tokens per task**.

### OPT-03: Emit-By-Exception Output Schema

Modify `stage-output-schema.md` to adopt an "omit by default, emit on exception" model:

- Optional fields are silent (omitted) when they carry no meaningful value. No more `none`, `not_applicable`, or empty sections.
- Required fields are only those that a meaningful stage output must always contain.
- All role-specific output requirements in individual agent prompts are converted to a compact checklist instead of prose paragraphs.

For example, a planner work order for a trivial typo fix goes from 40 fields (~2000 tokens) to:

```
task norm: fix typo in foo.py
files: [foo.py]
risk: local
helpers: none (trivial, applied lightweight profile)
success: typo corrected, no regressions
```

Estimated savings: **~1000-1500 tokens per agent per output**.

### OPT-04: Policy File Consolidation

Merge closely related workflow policies to reduce reference count and file I/O:

| Current | Merge Target | Rationale |
|---|---|---|
| `workflow-memory.md`, `lessons-guidance.md` | `memory-and-lessons.md` | Both memory; lessons-guidance.md is 20 lines |
| `review-output.md`, `review-helper-context.md` | `review-protocol.md` | Both review protocol; helper-context is 30 lines |
| `candidate-capture.md` sections into `control-policy.md` | `control-policy.md` (extended) | Already cross-referenced; duplicate content |
| `interface-consistency.md` sections into `agent-boundaries.md` | `agent-boundaries.md` (extended) | Interface surfaces are part of agent boundaries |

Estimated savings: 14 files → 10 files (29% reduction). Fewer `Load` directives per agent. **~500-1000 tokens per task** from reduced instruction references.

### OPT-05: Truly Lightweight Profile

Make the `lightweight` workflow profile genuinely skip stages instead of just differently emphasizing them:

Current lightweight behavior: "low-risk documentation, metadata-only, or narrow no-code tasks with no architecture, external dependency, or major verification risk." But the full guarded chain (planner → builder → reviewer → reflection → reporter) still runs with all helpers available.

Proposed lightweight behavior for tasks under ALL of these thresholds (local blast radius, ≤3 files, no behavior change, no interface touch, no architecture impact):

- Planner: direct work order production via `workflow_mode: delivery`, skip discovery/contract/architecture/lessons/memory/systems-engineering unless a risk trigger explicitly fires
- Builder: implement directly, skip verifier/review-completeness/review-architecture/review-lessons; use only build-error-resolver/cleanup if needed
- Reviewer: single-stage review (no helper sub-agents); skip verifier, skip all review helpers
- Reflection: skip entirely; set `reflect: not_applicable`
- Reporter: single-pass summary; no improvement candidates processing needed

This reduces agent invocation count from ~10-15 to ~3-4 per trivial task. Estimated savings: **~5000-12000 tokens per task** (6-11 fewer subagent invocations × ~1000 tokens each).

### OPT-06: ID-Based Handoffs

Replace full-text handoff payloads with task-ID references to written plan files and structured change manifests:

- Planner writes a compact plan file (already required under `plan-summary-schema.md`).
- Builder receives only `task_id` + work order scope; reads plan, contract, and risk context from disk.
- Reviewer receives only `task_id` + builder change manifest; reads plan, builder evidence from disk.
- Reflection and reporter receive only `task_id`; read accumulated artifacts from disk.

This eliminates passing the same context (requirements, file lists, architecture constraints) through 5+ agent handoffs. Estimated savings: **~2000-5000 tokens per task** depending on task complexity.

### OPT-07: Compact Permissions Using Tool Categories

Replace repeated per-agent permission blocks:

```yaml
permission:
  read: deny
  glob: deny
  grep: deny
  list: deny
  edit: deny
  write: deny
  bash: deny
  external_directory: deny
  webfetch: deny
```

With named categories in a shared file:

```yaml
profile: read_only  # expands to read/glob/grep/list allow, edit/write/bash deny
profile: full_access  # expands to all allow
profile: planner  # read/glob/grep/list/edit/write/bash allow, task allow specific
```

Reference the profile class instead of 10-12 lines of explicit tool permissions. Estimated savings: **~100-200 tokens per agent per file load**.

### OPT-08: Streamlined Subagent Lifecycle Decisions

In `subagent-lifecycle.md`, make `reuse_decision` and the entire `helper_lifecycle` block optional:

- Default: first-call helpers silently use `not_applicable` instead of explicitly declaring it.
- Only emit `helper_lifecycle` when the owning stage decides to reuse an existing helper after prior work.
- Remove `prior_context_dependency`, `context_rot_risk`, and `handoff_summary` from lifecycle output; these are already compacted into the reuse decision rationale.

Estimated savings: **200-500 tokens per first-call helper** × 5-10 helpers = **~1000-5000 tokens per task**.

## Expected Benefit

Combined, these seven optimizations reduce per-task token consumption for common scenarios:

| Task Size | Current (est. tokens) | Optimized (est. tokens) | Reduction |
|---|---|---|---|
| Trivial (typo fix, metadata update) | 25,000-35,000 | 8,000-12,000 | ~65-70% |
| Small (contained feature, 1-3 files) | 40,000-60,000 | 18,000-30,000 | ~50-55% |
| Medium (cross-module, interface touch) | 80,000-120,000 | 50,000-75,000 | ~35-40% |
| Large (destructive, revision loop) | 150,000+ | 100,000+ | ~30-35% |

Secondary benefits:
- Reduced context-window pressure for long-running tasks with revision loops
- Faster agent warm-up on simple requests (fewer subagent invocations)
- Cleaner agent prompts that are easier to maintain
- Lower cost-per-task in API-based deployments
- Reduced cognitive load when reading agent prompts

## Risk And Blast Radius

Medium blast radius — changes touch agent prompts (20 files), workflow policies (14 files), and output schemas. All seven OPTs are designed as isolated, independently verifiable delivery contracts, so partial implementation is safe.

Specific risks:

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| Agent behavior regression from consolidated instructions | Low | High | Each agent's effective prompt must be verified equivalent pre/post by diffing the rendered system prompt |
| Missing a required output field after schema change | Medium | Medium | Reviewer must check completeness against the old output schema; transitions can use a compatible dual-format period |
| Orchestrator removal breaks routing for non-planner entrypoints | Low | High | Verify that no external process or MCP routing references the `orchestrator` agent by name before removal |
| `_common-policies.md` reference syntax not supported | Low | Medium | Fall back to inlining the boilerplate in each agent; common-policies approach is just a readability/comprehensibility optimization |

Schemas are always extendable; agent prompts never lock out critical behavior. Any single OPT can be rolled back independently if issues arise.

## Suggested Priority

High

Token efficiency directly impacts the effective reasoning budget and task throughput. The `lightweight` profile optimization (OPT-05) alone can be implemented as a standalone contract with low blast radius and immediate benefit.

## Out Of Scope

- Do not change the actual agent permission boundaries or behavioral contracts — only how they are described, referenced, and transmitted.
- Do not change the routing logic, approval gates, or stage sequencing. The guarded chain (planner → builder → reviewer → reflection → reporter) stays intact for standard/high_assurance profiles.
- Do not change the IO format between the workflow and any external tooling or MCP integrations.
- Do not remove any functionality — only compress, consolidate, or skip it under defined conditions.

## Traceability

- Product: `.opencode/agents/` (all 20 agent files), `.opencode/dev_harness/workflow/` (14 policy files), `.opencode/dev_harness/workflow/stage-output-schema.md`, `.opencode/dev_harness/workflow/subagent-lifecycle.md`, `.opencode/dev_harness/instructions.md`, `.opencode/dev_harness/README.md`.
- Architecture: Instruction compression changes agent prompt construction (no architectural impact). Agent consolidation changes the invocation graph. Lightweight profile changes helper selection logic.
- Implementation: 3-5 delivery contracts per the task contract seed above. Each contract independently testable via diff review of rendered system prompts.
- Verification: For each OPT, render the effective system prompt for each affected agent before and after the change, diff them, and verify that the functional behavior is preserved and only redundant/verbose content is removed.
