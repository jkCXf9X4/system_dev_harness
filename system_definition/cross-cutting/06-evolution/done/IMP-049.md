## Theme

Fold the orchestrator-validation stage into the reviewer as a parallel helper to eliminate serial latency and enable concurrent execution.

## Evidence

- `.opencode/agents/orchestrator-validation.md` line 17: `task: "*": deny` — validation cannot invoke subagents or run in parallel with other checks.

## Current Pain Or Risk

The current architecture adds a serial validation stage between builder and reviewer. This creates:

1. **Serial latency**: Builder evidence must be inspected by validation before the reviewer can begin. For tasks where validation is required, the reviewer waits even when other review checks (architecture, completeness, lessons, verification) could start immediately.

2. **Double-check overhead (KM-004)**: Both validation and reviewer independently check VAL-001 through VAL-005 criteria. IMP-047 proposes separating responsibilities, but an alternative is to fold validation into the reviewer's parallel-helper model so the checks run once as part of a concurrent review pass.

3. **Inconsistent parallelism**: The reviewer can run multiple helpers in parallel (verifier, review-architecture, review-completeness, review-lessons), but validation is a separate serial stage that runs before any of them. This creates an unnecessary sequential bottleneck.

4. **Routing complexity**: The planner has special-case routing for validation outcomes (pass/fail/not_applicable/user_feedback_required) alongside reviewer routing (approved/blocked/waiver_required). Merging them simplifies the routing model.

## Proposed Improvement

Fold `orchestrator-validation` into the reviewer's parallel-helper model:

1. Make `orchestrator-validation` a reviewer-invoked helper (like verifier, review-architecture, review-completeness, review-lessons).
2. Update reviewer permissions to allow invoking `orchestrator-validation` as a task.
3. The reviewer invokes validation as a parallel helper alongside other review helpers when builder evidence becomes available.
4. The reviewer gate incorporates validation findings (pass/fail) into its overall gate decision: validation `fail` becomes a reviewer `blocked` with validation findings as blocking gaps.
5. Remove validation as a separate serial stage from the guarded chain in `control-policy.md`.
6. Remove validation-specific routing logic from `orchestrator-planner.md` (lines 39-42).
7. Update `reviewer-triggers.md` to move validation triggers into reviewer triggers.
8. Update `agent-boundaries.md` to reflect validation's new role as a review helper.

Validation criteria are preserved — they are checked as part of the review pass rather than as a separate stage.

## Expected Benefit

- **Parallel execution**: Validation runs concurrently with verifier, review-architecture, review-completeness, and review-lessons, eliminating serial latency.
- **KM-004 resolution**: Single authoritative check of VAL-001 through VAL-005 by the validation helper within the review pass; no double-check.
- **Simplified planner routing**: One less routing branch in the planner — only reviewer outcomes to handle.
- **Simplified guarded chain**: `planner -> builder -> reviewer -> reflection -> reporter` (validation is inside reviewer, not a separate stage).
- **Consistent parallelism model**: All review-time checks use the same parallel-helper pattern.

## Risk And Blast Radius

Medium — changes to multiple agent files, policy files, and the chain definition. Specific risks:

- **Gate authority**: Currently validation `fail` routes back to planner for revision before reviewer sees the work. If validation is folded into reviewer, a validation `fail` would surface as a reviewer `blocked`. This shifts the validation check from "pre-review advisory" to "part of gate decision." The reviewer must be designed to distinguish between validation-blocked (intent gap) and other-blocked (implementation quality gap) findings.

- **Not_applicable path**: Currently validation can return `not_applicable` independently (config changes, trivial fixes). If folded into reviewer, the reviewer must handle the not_applicable skip for validation specifically.

- **Affected files**: `orchestrator-planner.md` (remove validation routing), `orchestrator-reviewer.md` (add validation helper invocation), `orchestrator-validation.md` (convert to review-helper mode), `control-policy.md` (remove validation from required stages), `reviewer-triggers.md` (move validation triggers to reviewer section), `agent-boundaries.md` (update read-only agents list).

- **Depends on IMP-047**: IMP-047 addresses the VAL responsibility overlap but keeps two stages. IMP-049 is an alternative architectural direction. Only one should be implemented — they are mutually exclusive approaches.

## Notes

This is an alternative approach to IMP-047. IMP-047 keeps two separate stages and separates their responsibilities. IMP-049 proposes a more radical simplification: fold validation into the reviewer entirely, making it a parallel helper. Both approaches solve the KM-004 double-check problem. IMP-049 additionally solves the serial latency problem.

The key trade-off is gate authority: if validation is inside the reviewer, a validation failure can no longer return to the planner for revision before the reviewer sees the work. Instead, validation failure becomes one finding among several in the reviewer's gate decision. This is architecturally cleaner (single gate authority per PD-003) but requires the reviewer to handle validation findings distinctly from other review findings.
