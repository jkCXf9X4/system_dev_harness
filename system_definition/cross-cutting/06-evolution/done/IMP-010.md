## Current Pain Or Risk

When a planner or builder identifies a nontrivial improvement or design choice, the current chain offers no structured mechanism for iterative discussion, async review, or approval cycles before committing to action. Decisions are made inline within task execution, which:

- Makes it hard to revisit or challenge assumptions before work begins.
- Leaves no traceable discussion record for future reviewers.
- Forces high-judgment decisions into a single-pass execution model.
- Creates pressure to either accept the first proposal or waste time in unstructured back-and-forth.

## Proposed Improvement

Evaluate and propose a lightweight discussion stage or iterative feedback loop that fits into the existing guarded chain. Potential approaches include:

- **RFC-style proposal + async review window**: The planner or builder writes a short proposal (`system_definition/cross-cutting/06-evolution/selected/<proposal>.md`), a configurable review window opens, and execution proceeds only after approval or timeout.
- **Multi-step plan-draft-approve-execute cycle**: An explicit "draft" sub-stage between planner and builder where the operator can request revisions, approve as-is, or reject with rationale before builder execution begins.
- **Candidate discussion hook**: When an improvement candidate is surfaced during candidate-capture mode, the workflow pauses for a brief structured discussion before committing the candidate file to disk.

The chosen approach would be documented as part of the existing guarded chain, with clear triggers (e.g., when blast radius is high, when the planner flags a design decision, or when candidate-capture mode finds a nontrivial improvement).

## Expected Benefit

Adds structured collaboration to the workflow without breaking the single-pass execution model for simple tasks. Creates a traceable discussion record for design decisions, reduces rework from premature commitments, and improves the quality of improvement candidates by allowing brief iteration before persistence.

## Risk And Blast Radius

Medium to high. Adding a new stage or sub-stage to the guarded chain affects all downstream stages (planner, builder, reviewer, verifier). The design must be lightweight enough that it does not add friction for trivial tasks. The blast radius includes workflow control-policy, stage prompts, and candidate-capture lifecycle.

## Task Contract Seed

1. Evaluate the three approaches (RFC-style, multi-step cycle, candidate discussion hook) against the existing guarded chain constraints.
2. Propose a single approach, document the new stage or sub-stage in `.opencode/dev_harness/workflow/control-policy.md`.
3. Update the planner and builder prompts to recognize discussion triggers.
4. Define an output format for discussion artifacts (proposal files, review comments, approval decisions).
5. Add a transition rule from discussion to execution (approve, reject with rationale, request revision).
6. Document how candidate-capture mode interacts with the discussion stage.

## Out Of Scope

- Replacing the existing single-pass execution model for simple or low-risk tasks.
- Adding role-based access control or multi-human approval.
- Building a separate discussion platform or UI — all artifacts stay as markdown files in the repository.
- Modifying the reviewer or verifier stages beyond the discussion-to-execution transition.

## Notes

This candidate is related to IMP-008 (Pre-Execution Approval) but addresses a distinct gap. IMP-008 gates execution based on risk criteria (large-job definition), while IMP-010 provides a structured collaboration loop for iterating ideas before committing. If both are implemented, IMP-010's discussion stage could feed a risk assessment that IMP-008 uses for its pre-approval gate.
