## Theme

Reconcile the candidate-capture chain definition in `control-policy.md` with the planner routing behavior in `orchestrator-planner.md` to eliminate documentation inconsistency.

## Evidence

- `control-policy.md` line 118: includes `orchestrator-validation` in the candidate-capture chain (`planner -> builder -> validation -> reviewer -> reflection -> reporter`).
- `orchestrator-planner.md` line 47: states validation is `not_applicable` for candidate-capture mode.
- Source: BC-002 from IMP-026 reviewer findings.
- Plan file: `.opencode/dev_harness_plans/2026-06-30_160000-IMP-026.md`

## Current Pain Or Risk

The chain definition says validation runs in candidate-capture mode, but the planner routing says it is `not_applicable`. Future agents may be confused about whether validation should actually be invoked during candidate-capture. This is a documentation consistency gap — the chain definition and routing behavior disagree, creating ambiguity about the actual workflow.

## Proposed Improvement

Reconcile the chain definition in `control-policy.md` with the planner routing behavior. Either:
- **Option A**: Document that validation is always `not_applicable` for candidate-capture (the chain reference is informational only, listing the full chain for completeness but noting the per-stage applicability).
- **Option B**: Adjust the chain to note the conditional — e.g., annotate `validation` with `(not_applicable in candidate-capture mode)`.

## Expected Benefit

Eliminates ambiguity about whether validation invokes during candidate-capture. Future agents reading either `control-policy.md` or `orchestrator-planner.md` will find consistent information.

## Risk And Blast Radius

Low — documentation clarification only. No code or agent changes. Affects `control-policy.md` (one line) and possibly `orchestrator-planner.md` if the routing comment is also clarified.
