## Theme

Model caching optimization

## Evidence

- OpenCode's Anthropic provider (internal/llm/provider/anthropic.go) uses `cache_control` headers with `CacheControlEphemeralParam{Type: "ephemeral"}` on system messages, last tool definition, and last 3 messages
- OpenCode's OpenAI provider reads cached tokens from API response but does not explicitly set cache markers
- Workflow uses OpenRouter with DeepSeek models — caching support is provider-dependent
- Agent prompts mix static content (role description, policy references, output format) with dynamic content (task-specific instructions, file lists, work order) throughout the prompt body
- OpenCode's `autoCompact` feature monitors token usage and triggers summarization at 95% of context window, but this is a session-level fallback, not a content optimization strategy

## Current Pain Or Risk

Agent prompts interleave static policy references with dynamic task context throughout the prompt body. If the model/provider supports any form of prefix caching (Anthropic prompt caching, DeepSeek prefix caching, or generic KV-cache reuse), the current interleaved organization prevents effective cache utilization. Static content that could be cached across invocations is mixed with dynamic content that changes every time, reducing the contiguous static prefix available for caching.

## Proposed Improvement

Add a guideline to `_common-policies.md` or a new `prompt-authoring.md` file: place static content (role description, policy references, output format) at the beginning of prompts. Place dynamic content (task-specific instructions, file lists, work order) at the end. This maximizes contiguous static content at the prompt prefix for any provider that supports prefix-based caching.

## Expected Benefit

Variable — depends on provider caching support. With effective caching, static portions of agent prompts could achieve near-100% cache hit rates, reducing input token costs by 50-80% for cached portions. Even without explicit caching support, the reorganization is zero-cost and follows established software engineering best practices (separating stable from volatile concerns).

## Risk And Blast Radius

Very low — content reorganization only, no behavioral changes. No dependency on specific provider caching features. The reorganization cannot break functionality because no content is removed — only reordered.
