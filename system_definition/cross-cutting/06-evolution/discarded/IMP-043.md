## Theme

## Evidence

- `plan-summary-schema.md` — defines required fields but not section ordering or heading markers
- Existing plan files: 12-241 lines, 1-14KB (e.g., IMP-021: 15 lines/1KB, pb-se-alignment: 241 lines/14KB)
- `orchestrator-builder.md` prompt — loads full plan file from disk on receipt of `plan_file_path`
- `orchestrator-reviewer.md` prompt — reads full plan file to verify existence and check fields
- Builder needs: scope, files_touched, risk_assessment, tailoring_record, helper outputs, work order
- Reviewer needs: scope, risk_assessment, tailoring_record, success criteria

## Current Pain Or Risk

Plan files are loaded in full by builder and reviewer, even though each needs different sections. For large plan files (14KB), builder loads 14KB when it needs ~60%, reviewer loads 14KB when it needs ~50%. This means ~28KB of plan content loaded across two agents where ~40% is irrelevant to each. The cost grows with plan file size.

## Proposed Improvement

Add stable section markers to `plan-summary-schema.md` with mandatory headings: `## Scope`, `## Files Touched`, `## Risk Assessment`, `## Tailoring Record`, `## Helper Outputs`, `## Work Order`, `## Success Criteria`. Update builder prompt to use Read with offset/limit targeting builder-relevant sections. Update reviewer prompt for reviewer-relevant sections. Add section-order validation to plan file verification.

## Expected Benefit

30-50% reduction in plan file token usage per reader. Builder loads ~60% of plan file, reviewer loads ~50%, instead of 100% each. For a 14KB plan file, this saves ~6KB per reader.

## Risk And Blast Radius

Low — section markers are non-breaking additions to `plan-summary-schema.md`. Offset-based loading requires stable section ordering and plan-file-structure awareness. Mitigation: define mandatory section order in `plan-summary-schema.md`, add validation to plan file verification.
