## Current Pain Or Risk

Read-only agents (`orchestrator-researcher`, `orchestrator-reflection`, `orchestrator-reviewer`, review subagents) already follow a consistent permission pattern (`task: deny`, `edit: deny`, `write: deny`), but the pattern is implicit rather than codified. This means:
- New agents being onboarded have no explicit reference for the read-only permission boundary
- Auditors cannot easily verify that all read-only agents follow the same pattern
- The pattern could drift over time as agents are modified without a shared reference

## Proposed Improvement

Lightweight audit to confirm consistency of read-only permissions across all orchestrator-* agents, then codify the read-only permission pattern explicitly. This could take the form of a documented pattern in agent-boundaries documentation, a shared permission template, or a reference section that defines the canonical read-only agent permission set.

## Expected Benefit

Explicit, auditable read-only boundary; easier onboarding for new agents; reduced risk of permission drift over time.

## Risk And Blast Radius

Low — audit and documentation only; no behavioral change. The blast radius is limited to documentation files (agent-boundaries.md or equivalent) and possibly agent frontmatter comments. No runtime behavior, agent logic, or workflow control flow is affected.
