## Evidence

- `lessons.md` (271 lines, ~17KB) — 10 lessons covering diverse topics (architecture constraints, task tracking, interface consistency, folder layout, etc.)
- `patterns.md` (65 lines, ~4KB) — 1 pattern currently
- `orchestrator-memory.md` prompt — loads full memory files for every invocation
- `orchestrator-lessons.md` prompt — loads full lessons file for every invocation
- `orchestrator-review-lessons.md` prompt — loads full lessons file for every invocation
- Most tasks need only 1-3 relevant lessons, not all 10

## Current Pain Or Risk

Memory helpers load the full ~21KB of memory files for every invocation, even when only 10-20% is task-relevant. The filtering happens internally after loading, so the full content still consumes context window tokens. For `orchestrator-memory` and `orchestrator-lessons` called across planning and review stages, this means 21KB is loaded 2-3 times per workflow run with minimal utilization.

## Proposed Improvement

Add a lightweight pre-filtering step to the memory/lessons helper prompts: the calling stage provides task keywords or a scope description. The helper uses grep to identify potentially relevant entries (by matching keywords against lesson titles, scope fields, and trigger/revalidation conditions) before reading the full file. Only matching sections are loaded with Read offset/limit. Fall back to full-file loading when fewer than 2 matches are found or when uncertainty is high.

## Expected Benefit

60-80% reduction in memory file token usage per helper invocation. For a typical task needing 2-3 lessons, this saves ~15KB per memory helper call.

## Risk And Blast Radius

Low — pre-filtering could miss relevant entries if keywords don't match the lesson content. Mitigation: use broad keyword matching against title, scope, and trigger fields. Fall back to full-file loading when fewer than 2 matches are found or when the task scope is poorly defined.
