# IMP-009: Route Gate `blocked` To Planner For Automatic Revision Loop

## Status

Proposed

## Layer

Evolution

## Theme

Replace the strictly linear guarded workflow with a branching loop: when the completion gate returns `blocked`, route the review findings back to the planner for automatic re-scoping and re-execution.

## Evidence

- `.opencode/agents/orchestrator.md` lines 22-35 — Guarded workflow is listed as a flat sequence of 12 steps with no conditional branching. After step 11 (gate), step 12 (reporter) always runs regardless of gate result.
- `.opencode/agents/orchestrator-reviewer.md` — Returns `approved`, `blocked`, or `waiver_required` with `blocking gaps` and `next required action`. These fields are produced but never consumed by any downstream step.
- `.opencode/templates/workflow/review-output.md` — Review agents return `pass`, `fail`, or `needs_waiver` with structured findings and stable item IDs. This diagnostic information is discarded when the linear flow advances to reporter.
- `.opencode/agents/orchestrator-planner.md` — Has no input contract for revision context (prior findings, iteration count). It only normalizes an initial request.
- First-hand experience: the improvement workflow (IMP-001 through IMP-008) was produced in a single pass with no structural ability to loop on reviewer feedback.

## Current Pain Or Risk

A `blocked` gate result is informative but not actionable within the workflow. The orchestrator produces a final report saying "blocked — missing evidence" and stops. The human operator must manually re-run the entire workflow from scratch. All structured review findings (stable item IDs, specific gaps, next required action) are lost between runs because they exist only in the ephemeral conversation context of the completed run.

This breaks a core design goal from `docs/01-intent/vision.md`: "Every task has a checklistable requirement contract" and "Reviewer agents challenge completeness, requirements, architecture, QA, and mistake avoidance." If reviewer challenges cannot feed back into the work loop, they are audit-only rather than corrective.

Additionally, the current design creates perverse incentives: a human operator may accept a partial implementation rather than re-run the full 12-step workflow. The cost of restarting from scratch is higher than the cost of accepting a `waiver_required` outcome, which undermines the gate's authority.

## Proposed Improvement

Replace the linear "gate → reporter" tail with a branching loop:

```
step 11 (gate):
  if approved → step 12 (reporter) → end
  if blocked  → package review findings + iteration count → step 1 (planner)
  if waiver_required → present to human operator with waiver form → 
    if waiver accepted → step 12 (reporter) with waiver attached
    if waiver rejected → same as blocked
```

### Details

**Orchestrator branching (`.opencode/agents/orchestrator.md`):**
- Replace the flat step list with conditional routing after step 11.
- On `blocked`: collect all review outputs (findings with stable IDs, blocking gaps, next required action), set `revision=true`, increment `revision_count`, route to planner.
- Cap iterations at 3. On the 4th `blocked` with no improvement trend, escalate to human operator.

**Planner revision support (`.opencode/agents/orchestrator-planner.md`):**
- Accept an optional `revision` input block containing: prior review findings, blocking gaps, iteration count, original task normalization.
- Return the same plan shape but with refined scope addressing the blocking findings.
- Include a `revision_history` summary in the plan for downstream stages.

**Contract, architecture, lessons adjustments:**
- When `revision=true`, these stages receive the prior review findings alongside the new plan. They can relax, tighten, or clarify their previous output without starting from zero.
- Packet and builder run fresh with the corrected inputs.

**Cost guard:**
- If iteration count > 0 and the gate result is `blocked` with the same blocking gaps as the previous iteration (no improvement), escalate immediately rather than looping pointlessly.

## Expected Benefit

Reviewer findings become actionable within the workflow instead of being audit-only. The human operator does not need to manually re-run after a block. The cost of a single re-loop is lower than the cost of human re-execution, reducing the incentive to accept `waiver_required` for genuine gaps. The workflow matches its stated design goal: reviewer agents challenge and correct, not just audit.

## Risk And Blast Radius

**Blast radius:**
- `.opencode/agents/orchestrator.md` — Rewrite the guarded workflow section to add branching. High-impact change to the primary orchestrator prompt.
- `.opencode/agents/orchestrator-planner.md` — Add revision input contract. Medium impact.
- `.opencode/agents/orchestrator-contract.md`, `orchestrator-architecture.md`, `orchestrator-lessons.md` — May need minor updates to accept `revision=true` context and prior findings. Low-medium impact per agent.
- `.opencode/templates/workflow/control-policy.md` — Add policy for revision caps, escalation, and the `revision` control flag. Low impact.

**Risk:**
- **Infinite loops.** Mitigated by iteration cap (3) and no-improvement detection.
- **Planner overload.** If review findings are vague, the planner cannot refine meaningfully. Mitigation: the gate must reject vague findings before they enter the loop (it already requires stable item IDs).
- **Conversation context growth.** Each iteration adds findings, plans, and evidence. After 3 iterations the context may be large. Mitigation: use summary artifacts written to disk per iteration (see IMP-008).
- **Cost.** Each iteration re-runs 11 agent stages (planner through gate). For a 3-iteration max, this is 3x the normal agent cost. Acceptable for correctness-critical workflows.

## Suggested Priority

High — This is a workflow integrity issue. Without it, the gate is a suggestion, not a control. It directly affects the core thesis of the package (separate execution from approval, make review binding).

## Task Contract Seed

Update `.opencode/agents/orchestrator.md` to replace the linear step list with conditional routing on gate result. Update `.opencode/agents/orchestrator-planner.md` to accept a `revision` input with prior findings. Add iteration cap and escalation policy to `.opencode/templates/workflow/control-policy.md`. Run a test where a known-faulty implementation is submitted to verify the loop routes `blocked` → planner → re-execution → `approved` on the second pass.

## Out Of Scope

- Changing review agent behavior (they already return structured findings; those are the input to the loop).
- Adding a GUI or external tooling for the escalation path (human operator interaction stays in the OpenCode conversation).
- Creating per-iteration summary artifacts (that is IMP-008; this candidate depends on it for persistence but can work without it by passing context in the task tool's result channel).
- Building automated test fixtures for the branching logic (the task contract should include manual verification via a probe run).

## Notes

This candidate has a subtle dependency on IMP-008. Without automatic persistence, each iteration's findings exist only in ephemeral task-tool context. With IMP-008 in place, per-iteration review findings are written to disk and available for the planner to load. The loop can work without IMP-008 (findings passed via task result), but it is more robust with it.

The iteration cap of 3 is a starting default. The control policy should allow the contract or packet to override it per-task (some high-risk changes may warrant more iterations; some trivial changes may warrant cap=1).
