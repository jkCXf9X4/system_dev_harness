# IMP-003: Create Missing Verification Layer Directory

## Status

Proposed

## Layer

Evolution

## Theme

Create `docs/04-verification/` with starter artifacts documenting how verification is currently handled across the workflow.

## Evidence

- `docs/` directory — No `04-verification/` directory exists. The slot is occupied by `04-technical-decisions/`.
- `.opencode/templates/product-breakdown/layers/04-verification.md` — Expected artifacts: acceptance-criteria.md, test-strategy.md, test-cases/, traceability-matrix.md, decisions/.
- `docs/README.md` — Current note: "verification is scattered across workflow verifier and review evidence in `.opencode/agents/`."
- `docs/03-system-architecture/architecture.md` — Describes verifier stage, review agents, and completion gate but the verification documentation lives implicitly in agent prompts rather than in a dedicated layer.
- `docs/05-implementation/implementation.md` — Stage map shows orchestrator-verifier with shell capability and read-only review agents, but verification responsibilities are distributed across multiple agent descriptions.

## Current Pain Or Risk

Verification is the most critical quality gate in the workflow, but there is no structured documentation about what acceptance criteria apply, what the test strategy is, or how traceability from requirements to tests is maintained. The information exists only as implicit behavior in agent prompts (verifier, reviewer, gate). This makes it hard to review, hard to audit for completeness, and hard to change without reading multiple agent files. Package maintainers must reverse-engineer verification policy from agent behavior.

## Proposed Improvement

Create `docs/04-verification/` with a minimal set of starter files:

- `docs/04-verification/acceptance-criteria.md` — Document the high-level acceptance criteria that the workflow must satisfy (e.g., "every task produces a contract," "every change is independently reviewed").
- `docs/04-verification/test-strategy.md` — Describe the verification approach: how the workflow tests are structured, what the verifier stage covers, what the review agents check, and how the gate aggregates findings.
- `docs/04-verification/traceability-matrix.md` — A stub matrix linking requirements (from contracts) to verification evidence (from verifier and review stages).
- `docs/04-verification/decisions/` — Empty decisions directory, ready for future verification-related decisions.

Content should be extracted from the agent prompts and architecture docs, not invented. The starter content is documentation of current behavior, not new policy.

Update `docs/README.md` to list `04-verification/` instead of noting that verification is scattered.

## Expected Benefit

Verification moves from implicit (in agent prompts) to explicit (in layer docs). A maintainer can answer "how is this product verified?" by reading one directory. The package aligns with the seven-layer template. Future verification decisions have a natural home.

## Risk And Blast Radius

**Blast radius:** New files only; no existing files moved or modified (except `docs/README.md` for the layer table update). No agent behavior changes. The content is descriptive, extracted from existing documentation and agent prompts.

**Risk:** The initial content might be incomplete or slightly misaligned with actual verifier behavior. Mitigation: mark initial content as "current behavior snapshot — verify against agent prompts" and plan a follow-up review.

## Suggested Priority

Medium — Cannot be created before IMP-001 (renumbering) and IMP-002 (moving decisions out of the `04-` slot), but has no other hard dependencies. The starter content does not depend on the directory rename.

Create an empty `decisions/` directory. Create a stub `traceability-matrix.md`. Update `docs/README.md` layer table.
