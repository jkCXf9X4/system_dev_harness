# IMP-006: Add Root-Level Traceability Map

## Status

Proposed

## Layer

Evolution

## Theme

Create `docs/traceability-map.md` documenting the cross-layer traceability chain from intent through operation.

## Evidence

- `.opencode/templates/product-breakdown/traceability.md` — Describes the traceability chain: Intent → Product capability → Use case → Requirement → Decision → Architecture artifact → Implementation artifact → Test/verification artifact. Recommends a root `traceability-map.md` for broad cross-layer maps.
- `.opencode/templates/product-breakdown/README.md` — Expected tree includes `traceability-map.md` at root level.
- Current `docs/` root — No `traceability-map.md` exists. Traceability is handled per-file via `## Trace Links` sections in vision.md, use-cases.md, product-commitments.md, architecture.md, and implementation.md.
- Individual trace links exist but there is no aggregated view that shows the full chain end-to-end.

## Current Pain Or Risk

Traceability is currently decentralized. Each file has its own `## Trace Links` section, but there is no single map showing how intent flows through product commitments into architecture, decisions, implementation, and verification. A reviewer checking whether a requirement is covered end-to-end must manually follow links across 5+ files. The package does not have the `traceability-map.md` that the template prescribes.

## Proposed Improvement

Create `docs/traceability-map.md` with:

1. A textual traceability chain showing the full flow: Vision → Product Commitments (PC-001–PC-010) → Use Cases (UC-001–UC-013) → Architecture (control flow, stable concepts, boundaries) → Technical Decisions (AD-001–AD-003, IMD-001–IMD-002) → Implementation artifacts (opencode.json, agents, templates) → Verification (verifier stage, review agents, completion gate) → Operation (README, deployment process).

2. A table per major capability (e.g., "Guarded Delivery," "Continuous Improvement," "Design Quality") showing the trace chain for that capability.

3. A mapping of PC-001–PC-010 to their downstream artifacts.

The content should be extracted and consolidated from the existing `## Trace Links` sections in each file. Where a trace link is missing or ambiguous, note it as a gap rather than inventing a link.

## Expected Benefit

A single file answers "what traces exist across the entire system?" without reading five layer directories. The package matches the template's expected root-level files. Gaps in the traceability chain become visible and actionable. Reviewers can verify coverage from intent to verification in one place.

## Risk And Blast Radius

**Blast radius:** One new file. No existing files moved or modified. No agent behavior changes.

**Risk:**
- The traceability map could fall out of sync with individual file trace-links. Mitigation: add a maintenance note at the top of the file: "Auto-generated from per-file trace-links. Update the source file's `## Trace Links` section when adding or changing a trace link."
- If the existing trace-links already have gaps, the map will surface them — that is the desired outcome.

**Mitigation:** Mark the initial version as "Snapshot — may have gaps. Cross-reference with per-file Trace Links sections until automated verification exists."

## Suggested Priority

Medium — Can be created independently after IMP-001 (renumbering) to avoid path references changing. Low content creation cost for high traceability value.

## Task Contract Seed

Read all `## Trace Links` sections from vision.md, use-cases.md, product-commitments.md, architecture.md, and implementation.md. Consolidate into a single `docs/traceability-map.md` with a chain diagram and per-capability trace tables. Add a maintenance note. Mark any ambiguous or missing links as gaps.

## Out Of Scope

- Creating an automated traceability checker (out of scope for documentation restructuring).
- Changing individual file trace-links (those stay as they are; this map is a consolidation).
- Verification traceability-matrix (that belongs in `04-verification/traceability-matrix.md` per the template — see IMP-003).
- Changing the `.opencode/templates/product-breakdown/` runtime payload.

## Traceability

- Intent: Vision.md — the chain originates here; the traceability map closes the loop back to intent
- Product: PC-006 — explicitly requires the intent→commitments→architecture→decisions→implementation→verification chain
- Architecture: Architecture.md — boundaries section references traceability
- Implementation: Implementation.md — lists all artifacts and their roles
- Verification: The map will connect to verification artifacts once IMP-003 creates them

## Notes

The existing `## Trace Links` sections are well-maintained. The consolidation should be straightforward extraction and grouping. The map should highlight the gap that verification and operation layers are missing (until IMP-003 and IMP-004 fill them).
