# IMP-008: Persist Improvement Candidates To Disk Automatically

## Status

Proposed

## Layer

Evolution

## Theme

Add a thin persistence step to the improvement workflow so candidates are saved to disk without requiring a human to do it manually.

## Evidence

- `.opencode/agents/orchestrator.md` line 41: "The improvement workflow never edits files."
- `.opencode/agents/orchestrator-improvement.md` lines 13-14: `edit: deny`, `bash: deny` — the exploration agent is permission-locked and cannot write.
- `.opencode/agents/orchestrator-reporter.md` lines 13-14: `edit: deny`, `bash: deny` — the reporter is also permission-locked.
- The first run of this improvement workflow (IMP-001 through IMP-007) produced 7 fully-formed candidates with structured content, but none were persisted until you asked explicitly.
- `docs/06-backlog/` now exists with `improvement-backlog.md` and `candidates/IMP-*.md`, but this was done manually by the orchestrator stepping outside the defined workflow.

## Current Pain Or Risk

Improvement candidates are inherently ephemeral. They exist only as text returned through the `task` tool's result channel and disappear when the conversation ends. Persisting them requires either:

1. A human manually requesting a save (friction, easy to forget).
2. The orchestrator ignoring its own "never edits files" rule (rule violation, unclear boundary).

Neither is acceptable for a workflow designed to feed a durable backlog. Over time, improvement discoveries are lost, patterns go unfixed, and the improvement workflow's value degrades because its output has no home.

## Proposed Improvement

Add an automatic persistence step to the improvement workflow without compromising the read-only nature of the exploration itself.

**Approach (recommended):** Add a step to the orchestrator's improvement workflow procedure. After `orchestrator-improvement` returns its candidates and `orchestrator-reporter` produces the report, the orchestrator itself writes the candidates to `docs/06-backlog/candidates/` and updates `improvement-backlog.md`. The orchestrator already has `edit: allow` and `bash: allow`.

This requires two changes:

1. **Update `orchestrator-improvement`** to produce structured output that can be mechanically written to files. Specifically, its output contract should include:
   - A `## Persistable Content` section (or a structured block) with the exact file paths and content for each candidate.
   - The overview table entries.

2. **Update `orchestrator.md` improvement workflow instructions** to add a persistence step:
   ```
   improved improvement workflow:
     improvement intake
       -> read-only discovery
       -> pressure analysis
       -> cleanup, refactoring, and other backlog-ready candidates
       -> final report
       -> PERSIST: write candidates to 06-evolution/backlog/candidates/ and update overview
   ```

**Alternative (not recommended):** Grant `orchestrator-improvement` narrow `edit: allow` scoped to `docs/06-backlog/candidates/`. This keeps the persistence inside the exploration agent but blurs the read-only boundary. The orchestrator-based approach is cleaner because it separates exploration (read-only, no side effects) from persistence (mechanical write, orchestrator-owned).

## Expected Benefit

Improvement candidates survive the conversation. The backlog grows automatically. The "never edits files" rule stays true for exploration agents — persistence is the orchestrator's mechanical step. No human needs to remember to ask "can you save that."

## Risk And Blast Radius

**Blast radius:** Two agent prompt files updated:
- `.opencode/agents/orchestrator-improvement.md` — output contract change (add `Persistable Content` section requirement).
- `.opencode/agents/orchestrator.md` — add persistence step to improvement workflow instructions.

No other files. No `docs/` content changes beyond what the persistence step writes (and those are the same candidates the workflow already produces).

**Risk:**
- The orchestrator could write garbled output if the improvement agent's output does not match the expected structured format. Mitigation: the orchestrator should validate that each candidate has the required fields (ID, filename, content) before writing.
- If the backlog directory structure does not exist yet (pre-IMP-007), the write fails. Mitigation: the persistence step creates `candidates/` if it does not exist.

## Suggested Priority

High — This is a workflow reliability issue that affects every improvement run. It should be implemented before any other candidate because it ensures all future improvement output is preserved.

## Task Contract Seed

Update `.opencode/agents/orchestrator-improvement.md` to require a `## Persistable Content` section in its output specifying exact filenames and content for each candidate. Update `.opencode/agents/orchestrator.md` to add a persistence step after the reporter step: read the improvement agent's structured output, create `docs/06-backlog/candidates/` if needed, write each candidate file, and update `improvement-backlog.md`. Verify with a test improvement run.

## Out Of Scope

- Changing the exploration behavior of `orchestrator-improvement` (it remains read-only, edit: deny).
- Changing the reporter behavior of `orchestrator-reporter` (it remains read-only, edit: deny).
- Adding persistence for any other workflow type (guarded delivery has its own builder stage; this is improvement-only).
- Creating the backlog directory structure (that is IMP-007; this candidate writes into it but does not create the initialization content).

## Notes

This is a meta-improvement: it improves the improvement workflow itself. It has no prerequisites (can be implemented before IMP-001 through IMP-007) but becomes more valuable once IMP-007 creates the canonical backlog directory. The recommended order is IMP-008 first, then IMP-007 (to initialize the backlog), then the structural migration candidates.

The key design constraint is that exploration stays read-only. The orchestrator is the right owner for persistence because it already has write permission and acts as the workflow coordinator. A separate persister subagent (e.g., `orchestrator-improvement-persister`) with narrow `edit: allow` on the backlog path is a viable alternative but adds agent count without clear benefit.
