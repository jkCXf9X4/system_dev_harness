## Current Pain Or Risk

The workflow already has structured feedback fields, including `user_feedback_required` and `user_feedback_request`, but the initial planning stage does not define concrete criteria for when uncertainty must stop the workflow for user clarification. The planner is told to state assumptions, open questions, and interpretation choices, but it can still proceed when the user request is ambiguous enough that a wrong assumption would create scope drift, incorrect route selection, or unnecessary implementation work.

## Proposed Improvement

Add an explicit clarification gate to the initial planner behavior and control policy. The planner should pause and ask the user when uncertainty affects any of:

- requested outcome: implement now versus capture candidate
- target artifact, module, feature, or document
- intended behavior or acceptance criteria
- scope boundary or out-of-scope work
- destructive, broad, or irreversible changes
- user preference that materially changes the solution
- external dependency, API, or documentation choice that cannot be resolved safely by research

The gate should also define when assumptions are acceptable:

- the ambiguity is low impact
- the likely interpretation is strongly implied by repository context
- the task is read-only review or discovery
- proceeding will not edit files or commit to durable product behavior

Planner output should include either:

- `clarification_status: not_needed` with assumption rationale, or
- `clarification_status: required` with one to three specific user questions and the blocked decision each question resolves.

## Expected Benefit

Reduces wrong-route planning, speculative implementation, and rework caused by ambiguous initial requests. It also makes user clarification a deliberate workflow mechanism instead of an ad hoc open-question field.

## Risk And Blast Radius

Low to medium. This primarily affects planner and control-policy prompts, but if made too strict it could increase unnecessary pauses for simple tasks. The criteria should bias toward asking only when ambiguity changes scope, route, safety, or acceptance.

## Notes

The key design point is to distinguish harmless assumptions from blocking uncertainty. Open questions should not automatically pause the workflow; only questions that materially affect route, scope, acceptance, safety, or durable behavior should do so.
