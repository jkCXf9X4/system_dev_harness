## Theme

PBS / Verification — Move verification artifacts into per-level horizontal views per INCOSE §1.3.5

## Evidence

- `product-breakdown/04-verification/acceptance-criteria.md` — Centralized verification layer containing all acceptance criteria for the entire system, decoupled from the system elements they verify.
- `product-breakdown/README.md` — Verification is listed as a separate top-level decomposition branch (layer 04), sibling to intent, product, architecture, implementation, operation, and evolution.
- `SE_V5/INCOSE_SEHB5.txt` lines 1588–1591 (§1.3.5) — States the horizontal view "includes requirements; integration, verification, or validation activities and results; various other related artifacts; and external elements." Verification belongs at each decomposition level, not centralized in one branch.
- `SE_V5/INCOSE_SEHB5.txt` lines 4747–4773 (§2.3.4.1) — Describes PBS as "a breakdown of the SoI into successively lower-level details of its physical architecture." Verification is a per-level concern.

## Current Pain Or Risk

- Centralized verification layer (04) decouples acceptance criteria from the system elements they verify. A change to an architecture element requires cross-referencing a separate directory for verification impact.
- It is difficult to assess whether a given system element is adequately verified because the verification artifacts live in a separate branch.
- The current structure contradicts INCOSE §1.3.5, which places verification in the horizontal view at each decomposition level, not in a separate vertical branch.

## Proposed Improvement

Move acceptance criteria and verification artifacts into per-element horizontal views. Each PBS element (intent, product, architecture, implementation, operation, evolution) would contain a local `verification/` subdirectory or file documenting how that element is verified. Maintain a cross-cutting traceability matrix at the top level to preserve system-wide verification coverage.

## Expected Benefit

- Verification is co-located with the element it verifies, making impact analysis simpler.
- Horizontal view aligns with INCOSE §1.3.5 recommendations.
- Changes to a system element automatically surface its verification criteria for review.
- Reduces the risk of verification gaps during element-level changes.

## Risk And Blast Radius

- Would scatter centralized `product-breakdown/04-verification/acceptance-criteria.md` across multiple locations (six or more directories).
- `product-breakdown/traceability-map.md` would need updates to reflect new verification locations.
- Agent prompts that reference `product-breakdown/04-verification/` would need path updates.
- Cross-cutting verification concerns (system-level acceptance criteria) could be lost unless explicitly preserved in the top-level traceability matrix.

- Creating verification artifacts for layers beyond the pilot scope
