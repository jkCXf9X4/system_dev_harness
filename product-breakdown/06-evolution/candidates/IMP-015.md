## Theme

PBS / Metadata — Annotate leaf elements with make/buy/reuse decisions per INCOSE §1.3.5

## Evidence

- `product-breakdown/03-implementation/implementation.md` — Lists implemented artifacts but does not declare element type (atomic vs. decomposable) or sourcing decisions.
- `product-breakdown/02-architecture/architecture.md` — Lists stable concepts and boundaries but does not annotate which elements are built, bought, reused, or derived from open-source dependencies.
- `SE_V5/INCOSE_SEHB5.txt` lines 1518–1528 (§1.3.5) — States: "A system element that needs only a black box representation to capture its requirements and confidently specify its real-world solution definition can be regarded as atomic. Decisions to make, buy, or reuse the element can be made with confidence without further specification of the element."
- `SE_V5/INCOSE_SEHB5.txt` line 1536 (§1.3.5) — References atomic vs. higher-level system elements in Figure 1.7 annotations including "Make, buy, or reuse."

## Current Pain Or Risk

- Current PBS has no `element_type` (atomic|decomposable) or `sourcing_decision` (make|buy|reuse|open-source-dependency) annotations on any element.
- Without atomic leaf identification, it is impossible to know which elements are candidates for make/buy/reuse decisions.
- Maintenance burden increases when it is unclear whether a given artifact is a custom build, a reused template, or an external dependency.
- New contributors cannot determine which elements are self-contained vs. which require further decomposition.

## Proposed Improvement

Add `element_type` (atomic|decomposable) and `sourcing_decision` (make|buy|reuse|open-source-dependency) fields to PBS element documentation. For each leaf element in the product tree, record:
- **element_type**: atomic or decomposable
- **sourcing_decision**: make (custom-built), buy (commercial), reuse (adapted from internal or known source), open-source-dependency (external OSS with known license)
- **rationale**: brief justification for the sourcing decision

Update `product-breakdown/product-tree.md` (when created per IMP-012/IMP-014) to include these annotations.

## Expected Benefit

- Make/buy/reuse decisions become explicit and auditable per INCOSE §1.3.5.
- Atomic leaf identification enables confident scoping of implementation tasks.
- Sourcing decisions document why an element is custom-built vs. adopted from an external source.
- Maintenance planning improves when it is clear which elements are external dependencies requiring upgrade tracking.

## Risk And Blast Radius

**Low** — metadata annotation only. Risks:
- Requires agreement on the `element_type` and `sourcing_decision` values for each leaf, which may involve discovery work.
- Some elements may mix sourcing (e.g., a template reused from an internal source and then customized).
- The annotations must be kept in sync with the product tree structure.
