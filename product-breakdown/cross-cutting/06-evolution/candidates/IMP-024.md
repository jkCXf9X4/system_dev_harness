## Summary

This evaluation examines whether `cross-cutting/05-operation/` (containing `runbook.md` and `deployment-process.md`) should be moved from the cross-cutting grouping into a dedicated PBS layer under `product-breakdown/pbs/`. The content is unambiguously PBS-nature (physical operational requirements and deployment constraints — not functional descriptions). However, no clean insertion point exists in the current PBS numbering scheme, the blast radius is 19+ unique files across the workspace, structural churn is high (this would be the third restructure of 05-operation), and IMP-021 has an active dependency on the current path. The evaluation recommends **Conditional Merge — defer until IMP-021 is resolved and a stable insertion point is established**, with a clear preference for keeping 05-operation in cross-cutting in the interim and strengthening its PBS-nature labeling.

## Current State

`cross-cutting/05-operation/` contains two files:

- **`runbook.md`** (Operational Product Requirements): 6 operational requirements describing how the workflow must behave at runtime (runability, blocked-work preservation, revision caps, waiver handling, stage feedback, failure recovery), plus 3 product boundaries (no individual reruns, no scope expansion, escape hatches guarded).

- **`deployment-process.md`** (Deployment Product Requirements): 5 deployment requirements describing how the package is deployed (copy-only deployment, target repository refresh, diff-based updates), plus 3 product boundaries (no registry, no installer, no target-repo SCM).

Both artifacts trace backward to PBS artifacts (`architecture.md`, `implementation.md`, `control-policy.md`) and forward to operator-facing docs (`docs/operation.md`, `docs/install-and-deploy.md`). There is no `decisions/` content — the directory is empty per `product-tree.md`.

## PBS Structure Analysis

### Current PBS Layer Conventions

Per `product-breakdown/pbs/README.md`:

| Layer | Description |
| --- | --- |
| `02-architecture/` | Architecture control flow, boundaries, decisions, and verification criteria |
| `03-implementation/` | Implementation artifacts, artifact map, and implementation-level decisions |

PBS artifacts describe **physical** architecture (agents, files, directories, decisions). `02-architecture` covers "How is it structurally organized?" `03-implementation` covers "How is it built in code and configuration?"

### Insertion Point Options

#### Option A: `pbs/04-operation/` — renumber existing 04

- **What it requires:** Create `product-breakdown/pbs/04-operation/` and either renumber `cross-cutting/04-verification/` or accept that `pbs/04-*` is a different concept from `cross-cutting/04-*`.
- **Verdict:** **Not feasible.** Renumbering `04-verification` would break every reference to it (60+ additional files). If `pbs/04-operation/` coexists with `cross-cutting/04-verification/`, the numbering collision is confusing — two layers claim "04" for different decomposition views.

#### Option B: `pbs/05-operation/` — accept a gap in PBS numbering

- **What it requires:** Create `product-breakdown/pbs/05-operation/`. The PBS would have `02`, `03`, `05` — a gap at `04`.
- **Verdict:** **Pragmatically possible but visually awkward.** The gap at 04 would need documentation explaining it ("04 is cross-cutting verification, which spans FBS and PBS"). This violates KM-006 (hierarchical layout scanability) because the numbered sequence is broken. The gap would also need ongoing maintenance — any new PBS layer must account for it.

#### Option C: Subsumed into `pbs/02-architecture/` or `pbs/03-implementation/`

- **What it requires:** Move `runbook.md` and `deployment-process.md` into `pbs/02-architecture/` or `pbs/03-implementation/`.
- **Verdict:** **Not appropriate.** Runbook and deployment requirements are operation-scoped concerns that do not fit under architecture (structural) or implementation (code/config). Subsuming would break the layer separation (KM-005) by mixing operational requirements with architecture or implementation.

#### Option D: `pbs/04-operation/` after shifting FBS numbering

- **What it requires:** Change PBS numbering to start at `01` instead of `02`, freeing `04` for operation. This would require renumbering `pbs/02-architecture/` → `pbs/01-architecture/` and `pbs/03-implementation/` → `pbs/02-implementation/`, plus updating every reference.
- **Verdict:** **High cost for marginal benefit.** Renumbering the PBS would break all path references across the workspace. The blast radius would exceed IMP-017's 40-file precedent.

**Preferred insertion point (if merged):** Option B (`pbs/05-operation/` with a gap at 04), with explicit documentation explaining the gap. No option is clean.

## Evaluation Criteria

### C1: Content Fit Assessment

**Verdict: The content is pure PBS-nature.**

`runbook.md` requirements describe:
- Physical execution constraints ("revision loops must stop at configured cap")
- Operational procedures ("blocked work must preserve gate findings")
- Physical boundaries ("no individual stage reruns")

`deployment-process.md` requirements describe:
- Physical deployment mechanism ("deployable by copying opencode.json and .opencode/")
- Physical refresh constraints ("target repos refresh without overwriting memory")
- Physical scope boundaries ("no registry, no installer")

Per INCOSE §2.3.4.1, these are physical architecture concerns — describing HOW the system is structured and operates, not WHAT functional behavior it provides. IMP-023 Q1 already classified this content as PBS-nature with strong evidence (Q1.2 content classification table).

The content references physical entities throughout: `control-policy.md`, `agent boundaries`, `operator path`, `opencode.json`, `.opencode/` directory. This would satisfy PBS conventions (G-02: trace to FBS but no duplicate functional descriptions) because the artifacts already trace to FBS via their trace links section without duplicating functional language.

### C2: Guardrail Compliance (G-02, G-08)

#### G-02: "PBS artifacts must trace back to FBS but not duplicate functional descriptions"

**Current compliance:** 05-operation artifacts satisfy G-02 today. `runbook.md` trace links reference `architecture.md` and `control-policy.md` but do not include FBS function statements. `deployment-process.md` references `implementation.md` and IMD-003.

**Post-merger compliance:** If moved to PBS, the artifacts would need explicit FBS trace links (e.g., "Satisfies: PC-001 through PC-010 operational concerns"). Currently neither file has FBS trace links. The gap-analysis.md (line 85) maps `cross-cutting/05-operation/` to "All functions (satisfies non-functional requirements)" — this is a mapping at the gap-analysis level, not in the artifacts themselves. **Moving to PBS would strengthen G-02 compliance** because the artifacts would be explicitly labeled as PBS, making their FBS traceability a design requirement rather than a loose annotation.

#### G-08: "Cross-cutting layers span both FBS and PBS without belonging exclusively to either"

**Current compliance:** 05-operation is listed as cross-cutting but its content is PBS-only. It does not "span both FBS and PBS" in practice — it is exclusively PBS-nature content. The cross-cutting README states "Operation requirements respond to functional needs for availability, reliability, and maintainability" which is a rationale for cross-cutting placement, but the actual artifacts do not contain FBS-spanning content.

**Post-merger impact:** Moving 05-operation to PBS would **remove a layer that was never truly cross-cutting in content** from the cross-cutting grouping. This clarifies the cross-cutting concept — remaining layers (04-verification, 06-evolution) are genuinely transversal. It does not weaken G-08; it strengthens it by removing a false cross-cutting member.

### C5: Lesson Compliance (KM-004 through KM-008)

#### KM-004 (Minimize Parallel Structures)

**Would moving 05-operation to PBS eliminate a parallel structure or create a new one?**

Currently, 05-operation lives in `cross-cutting/` which is a parallel-grouping to `pbs/`. Its content describes physical system operation — a PBS concern. Moving it to PBS eliminates this parallel structure by placing PBS-nature content in the PBS directory. This is a **positive** outcome for KM-004 — one fewer cross-cutting layer means less parallel structure.

However, there is a subtle risk: if 05-operation moves to PBS but verification (04) and evolution (06) remain in cross-cutting, the "operation" concept now exists in two mental models — physical (PBS) and transversal (what IMP-023 Q4 called "structural cross-cutting"). Documentation must clearly separate the PBS operation layer from the remaining cross-cutting concerns.

**Net:** KM-004 weakly supports the move (eliminates a parallel structure).

#### KM-005 (Preserve Layer Separation)

**Does PBS have a natural "operation" layer, or would this be forced?**

PBS currently has `02-architecture` (structural) and `03-implementation` (code/config). There is no natural "operation" layer precedent in the PBS. The PBS README does not mention operation. Per INCOSE §2.3.4.1, the PBS decomposes physical architecture into successively lower levels — "operation" is a lifecycle phase, not a structural decomposition axis. Operation artifacts are better described as **physical architecture artifacts about how the system runs**, which could fit under an augmented PBS definition.

If placed in PBS, 05-operation would need a clear role statement distinguishing it from architecture (structural) and implementation (code/config). A possible framing: "How is the system operated and deployed?" — answering a "how" question consistent with PBS conventions.

**Net:** KM-005 neither strongly supports nor opposes — the fit is plausible but requires explicit role definition.

#### KM-006 (Hierarchical Layout)

**Would `pbs/05-operation/` improve or degrade scanability?**

Currently:
```
pbs/
  README.md
  02-architecture/
  03-implementation/
```

With 05-operation:
```
pbs/
  README.md
  02-architecture/
  03-implementation/
  05-operation/
```

The gap at 04 degrades scanability (users wonder "where is 04?"). However, if the gap is documented (e.g., "04 is the cross-cutting verification layer"), it becomes navigable. The alternative of renumbering to fill the gap would be more disruptive.

If a future IMP creates `pbs/01-intent/` or `pbs/01-product/`, the numbering could be reshuffled — but that is speculative.

**Net:** KM-006 slightly opposes — the gap at 04 degrades scanability. But the impact is minor and can be mitigated with documentation.

#### KM-007 (Stale References)

**How many files would need path updates? Is the stale-reference risk manageable?**

19 unique files, ~30-35 reference updates. Most are find-and-replace (`cross-cutting/05-operation/` → `pbs/05-operation/`). The risk of missed references is moderate because:
- The pattern `cross-cutting/05-operation/` is distinctive enough for reliable grep-based replacement.
- However, some references use relative paths (e.g., `../05-operation/` in decision-placement.md, or `05-operation/verification.md` in verification.md).
- The `product-breakdown/cross-cutting/05-operation/` directory itself would need to be deleted or emptied, risking KM-007 (stale references) if any path string was missed.

**Mitigation required:** After moving, run a comprehensive audit: grep for `05-operation` across the entire workspace, check for broken relative paths, and verify all cross-references resolve.

**Net:** KM-007 is a moderate risk — manageable with thorough cleanup but the risk of a missed reference exists.

#### KM-008 (Orphaned Nodes)

**Would `cross-cutting/05-operation/decisions/` path references become orphans?**

The `product-tree.md` references `cross-cutting/05-operation/decisions/` (lines 134, 269). This directory does not exist on disk (grep confirmed, `ls` confirmed empty/absent). If 05-operation moves to PBS, the `decisions/` reference in product-tree.md would need to reference `pbs/05-operation/decisions/` — but this directory also does not exist.

If no decision records are ever placed in 05-operation/decisions/, the reference in product-tree.md is effectively a dead path regardless of merger. The merger does not worsen the orphan situation — it just changes the dead path from `cross-cutting/05-operation/decisions/` to `pbs/05-operation/decisions/`.

The `.opencode/dev_harness/product-breakdown/decision-placement.md` line 18 lists `05-operation/decisions/` as the canonical location for deployment/monitoring/support decisions. If 05-operation moves to PBS, this guidance must be updated to `pbs/05-operation/decisions/`.

**Net:** KM-008 is a low risk — the decisions/ path is already effectively dead. Merger does not introduce new orphan risk beyond the path string update.

### C6: IMP-017 Precedent (Restructuring Churn)

05-operation has been restructured three times:

1. **Pre-IMP-017:** Part of the flat numbered layout (`05-operation/` at product-breakdown root)
2. **IMP-017 (2026-06-29):** Moved to `cross-cutting/05-operation/` as part of FBS-PBS directory restructuring (40+ file updates)
3. **Proposed (IMP-024):** Move to `pbs/05-operation/`

The timeline is compressed: IMP-017 was completed today (2026-06-29). Proposing a third restructure on the same day creates **structural churn risk**. Agents trained on the current layout would need to unlearn-relearn the operation layer path. Documentation written today (IMP-023, IMP-021) references the cross-cutting path — immediately invalidated.

Per PAT-002 step 6: "When MECE purity conflicts with practical architecture, resolve in favor of pragmatic retention." And step 7: "If a sequencing path exists (reduce scope first, then re-evaluate removal), prefer that over a single high-risk restructure."

**IMP-017 precedent suggests:**
- Restructuring cost is real and significant (40+ files, multiple README updates)
- The current path is only hours old — agents have no time to form navigation habits that need breaking
- The cost-benefit of a second immediate restructure is negative: the content classification benefit (PBS placement) is theoretical while the disruption cost is immediate

### C7: IMP-021 Interaction

IMP-021 proposes creating `cross-cutting/05-operation/verification.md` as part of per-layer verification criteria distribution. It references this path in lines 32, 44, and 68.

**If 05-operation moves to PBS before IMP-021 is resolved:**
- IMP-021's path references become stale (need to change `cross-cutting/05-operation/verification.md` to `pbs/05-operation/verification.md`)
- The verification.md creation task in IMP-021 (line 68) simplifies because the path is now a standard PBS path rather than a cross-cutting path

**If 05-operation moves to PBS after IMP-021 is resolved:**
- The verification.md file would have been created at `cross-cutting/05-operation/verification.md` and would need to be moved to `pbs/05-operation/verification.md`
- All cross-references in verification.md would need updating

**Would PBS merger complicate or simplify IMP-021's intent?**

IMP-021's intent is INCOSE-aligned per-layer verification. If 05-operation is a PBS layer, creating a verification.md there is more natural — it follows the pattern established by `pbs/02-architecture/verification.md` (IMP-013 pilot). The verification.md would be a PBS element's horizontal view, not a cross-cutting layer's horizontal view. This is actually cleaner INCOSE alignment.

**However**, resolving IMP-021 first (creating the verification.md in 05-operation) and then moving 05-operation to PBS would create unnecessary churn — the verification.md file would need to be moved twice (create, then move with the directory). The cleaner sequence is: **move 05-operation to PBS first, then resolve IMP-021** so the verification.md is created at the final location.

**Net:** IMP-021's intent is simplified by PBS placement. But the sequence matters — merge first, then IMP-021.

## Recommendation

### Conditional Merge — defer until IMP-021 is resolved and a stable insertion point is established

**Evidence summary:**

| Criterion | Assessment |
|-----------|------------|
| C1: Content Fit | **Strong positive** — PBS-nature content |
| C2: G-02 Compliance | **Positive** — strengthens G-02 by making FBS trace links a design requirement |
| C2: G-08 Impact | **Positive** — clarifies cross-cutting by removing a non-transversal layer |
| C3: Traceability Impact | **Low complexity** — 6-7 path updates in 4 files |
| C4: Blast Radius | **Moderate** — 19 files, ~30-35 updates (less than IMP-017's 40+) |
| C5: KM-004 | **Supports** — eliminates parallel structure |
| C5: KM-005 | **Neutral** — plausible fit with explicit role definition |
| C5: KM-006 | **Slightly opposes** — gap at 04 degrades scanability |
| C5: KM-007 | **Moderate risk** — manageable with grep-based cleanup |
| C5: KM-008 | **Low risk** — decisions/ path is already effectively dead |
| C6: IMP-017 Churn | **Strongly opposes immediate move** — third restructure on same day |
| C7: IMP-021 Interaction | **Sequence-dependent** — merge first, then IMP-021 |
| C8: Cross-Cutting Residual | **Neutral to slightly positive** — smaller, more coherent cross-cutting |

**Primary arguments for deferral:**

1. **Structural churn (C6):** IMP-017 was completed today (2026-06-29). Proposing a third restructure of the same layer on the same day creates unnecessary disruption. The current cross-cutting location is only hours old — agents have no established navigation habits. However, the change cost is real (19+ files) and the benefit is theoretical (cleaner PBS alignment).

2. **Imperfect insertion point (PBS Analysis):** No clean `pbs/04-operation/` insertion point exists without renumbering or accepting a gap at 04. The gap degrades scanability (KM-006) and requires ongoing documentation.

3. **IMP-021 sequence dependency (C7):** IMP-021's verification.md creation in 05-operation should resolve after the merger, not before. Merging now would invalidate IMP-021's draft; deferring until IMP-021 is scoped allows coordinated sequencing.

**Recommendation details:**

| Aspect | Guidance |
|--------|----------|
| **Immediate action** | Keep 05-operation in cross-cutting. Strengthen its PBS-nature labeling (e.g., add "This layer is PBS-nature — it describes physical operational requirements, not functional behavior" to the cross-cutting README description). |
| **Deferral trigger** | Defer PBS merger until IMP-021 is resolved (or at least until a task contract exists). |
| **Merge condition** | Merge when: (a) IMP-021 has created the verification.md in 05-operation's current path, OR (b) IMP-021 is explicitly sequenced after the merger. |
| **Preferred insertion point** | `pbs/05-operation/` with documented gap at 04 (Option B). |
| **Alternative to merger** | If IMP-021 reaches done status and the gap at 04 remains objectionable, consider renumbering PBS to close the gap (Option D) — but only if the blast radius analysis at that time is acceptable. |
| **Stabilization period** | If merged, allow at least 1-2 IMP cycles before any further restructuring of the operation layer. |

**Fallback recommendation:** If merging is deemed too costly after IMP-021 resolution, keep 05-operation in cross-cutting permanently. The content is well-documented, the cross-cutting rationale (G-08) is defensible, and the practical cost of structural purity exceeds the navigational benefit of PBS placement. The cross-cutting README should include an explicit note: "05-operation contains PBS-nature content but remains in cross-cutting to avoid disruptive renumbering of the PBS layer sequence."
