## Current Pain Or Risk

The decomposition model currently has a cross-cutting grouping (`cross-cutting/04-verification`, `05-operation`, `06-evolution`) whose placement is questioned against INCOSE/ISO 15288 MECE (Mutually Exclusive, Collectively Exhaustive) principles. The INCOSE standard prescribes that all decomposition elements should belong to exactly one of FBS, PBS, or WBS. The current cross-cutting grouping violates this strict MECE alignment, creating a structural ambiguity:

1. Should 05-operation (operational requirements, deployment model) be under FBS as operational functions?
2. Should 06-evolution (wbs.md, improvement lifecycle tracking) be under a formal WBS?
3. Can the cross-cutting grouping be eliminated entirely, with contents cleanly redistributed?
4. What is the current boundary adherence quality and what improvements are possible?

Until these questions are resolved, the decomposition model has a structural tension that may confuse new contributors and creates a precedent for ad-hoc grouping rather than principled decomposition.

## Proposed Improvement

This candidate is a **structured evaluation** answering four decomposition model questions. It does not propose immediate implementation — it produces a decision-support artifact that a future scoped task can act upon. The evaluation is structured around INCOSE/SE best practices, current artifact content analysis, architecture guardrails, lessons learned, and blast-radius assessment.

The full evaluation follows.

# FBS/PBS/WBS Cross-Cutting Decomposition Evaluation

## Summary

This evaluation examines whether the cross-cutting grouping in the product-breakdown hierarchy (`cross-cutting/04-verification`, `05-operation`, `06-evolution`) should be redistributed into FBS, PBS, or WBS per INCOSE/ISO 15288 best practices. After analyzing current artifact content, architecture guardrails, lessons learned, and blast radius, the evaluation concludes: **do not restructure cross-cutting at this time.** The cross-cutting grouping serves a genuine transversal purpose (concerns that span multiple FBS functions and PBS components) that pure MECE decomposition would lose. The blast radius is large (17–60 files referencing each directory), the content classification is mixed (partial fits to FBS/PBS/WBS within each layer), and the precedent of IMP-017 (40+ file updates for directory restructuring) demonstrates the cost. The recommended path is incremental: strengthen labeling and cross-references within the existing cross-cutting structure rather than redistributing content. Incremental boundary improvements within individual layers (e.g., ensuring FBS artifacts avoid physical references) are worthwhile but independent of the cross-cutting question.

## Question 1: 05-Operation Under FBS

### Q1.1 Current State

The `cross-cutting/05-operation/` directory contains two files:

- **`runbook.md`** (Operational Product Requirements): Lists 6 operational requirements — "Operators must be able to run the workflow", "Blocked work must preserve gate findings", "Revision loops must stop at configured cap", "Waiver handling must expose named risk", "Stage feedback must be explicit", "Stage failures must have conservative recovery path." Also lists product boundaries (no arbitrary reruns, escape hatches must not weaken default path).

- **`deployment-process.md`** (Deployment Product Requirements): Lists 5 deployment requirements — deployable by copying `opencode.json` and `.opencode/`, target repos must refresh without overwriting repo-local memory, deployment updates reviewable as diffs. Also lists product boundaries (no registry, no installer, no target-repo SCM).

### Q1.2 Content Classification (FR-1.1)

The content of both files is **PBS-nature, not FBS-nature**. Specifically:

**`runbook.md` content classification:**
| Requirement | Nature | Rationale |
|---|---|---|
| "Operators must be able to run the workflow" | Non-functional / operational constraint | Describes HOW the system must behave at runtime, not WHAT function it performs |
| "Blocked work must preserve gate findings" | Process requirement | Describes operational procedure for blocked work — a physical workflow concern |
| "Revision loops must stop at configured cap" | Operational boundary | Physical constraint on workflow execution |
| "Waiver handling must expose named risk" | Operational procedure | Physical step-by-step operational behavior |
| "Stage feedback must be explicit" | UX / operational requirement | Describes operator interaction, not a system function |
| "Stage failures must have conservative recovery path" | Reliability requirement | Non-functional constraint on physical execution |

**`deployment-process.md` content classification:**
| Requirement | Nature | Rationale |
|---|---|---|
| "Deployable by copying..." | Deployment mechanism | Describes HOW to deploy the physical package |
| "Target repos must refresh without overwriting memory" | Deployment constraint | Physical deployment concern |
| "Deployment updates reviewable as diffs" | Deployment quality | Physical concern |
| Product boundaries (no registry, installer, etc.) | Scope constraints | Physical scope boundaries |

The content is operational requirements and deployment constraints — these are **non-functional requirements** and **physical deployment concerns**. INCOSE §2.3.4.1 distinguishes between operational functions (what the system does functionally) and operational requirements (how the system behaves during operation). The current content describes operational *how* and deployment *how*, not operational *what*.

### Q1.3 INCOSE/SE Best Practices (FR-1.2)

INCOSE §2.3.4.1 states that operational requirements belong in FBS **as operational functions** — i.e., reframed as functional statements about what the system must do during operation. For example, "The system shall provide operator notification of blocked work with preserved findings" is FBS-nature; "Operators must be able to run the workflow from a target repository" is a deployment constraint.

INCOSE §2.3.4.2 (physical architecture) places deployment modeling and operational procedures in the PBS as part of the physical architecture. The current content is closer to physical architecture than functional architecture.

**Researcher finding (INCOSE):** Operational requirements belong in FBS as operational functions.
**Architecture guardrail (G-01):** FBS artifacts must not reference file paths, agent names, or physical structure.
**Architecture assessment:** Moving 05-operation to FBS is high-risk — content is physical/PBS in nature, violates G-01 if moved as-is.

**Tension resolution:** The INCOSE principle is valid for operational *functions* (e.g., "the system shall maintain state across restarts") but the current 05-operation content describes *deployment procedures* and *runtime constraints* on physical agents, not operational functions. The content would need significant reframing to become FBS-compatible. The architecture guardrail G-01 is the stronger constraint because the current content references physical entities (control policy, agent prompts, file paths) throughout.

### Q1.4 Feasibility of Reframing (FR-1.3)

Reframing 05-operation content as functional statements is theoretically possible but pragmatically costly:

- **`runbook.md`** would need each requirement rewritten as "The system SHALL..." style functional statements (e.g., "The system shall expose blocked work findings to the operator with preserved gate findings and stable gap identifiers"). This is feasible but loses operational specificity — the current runbook explicitly references physical entities (control policy.md, agent boundaries.md, operator.md) that would need path-based cross-references, violating G-01.

- **`deployment-process.md`** would need to become "The system shall support deployment by copying opencode.json and .opencode/" — but this is inherently a physical deployment mechanism statement belonging to PBS.

- **Key difficulty:** Operational procedures (step-by-step "how to run the workflow") and deployment constraints (file copying, target repository structure) are inherently physical. Reframing them as functional statements produces awkward artifacts that stretch the FBS concept.

- **Recommendation on reframing:** Not worth the effort. The reframed content would be less precise, the physical traceability would be lost, and the result would be a FBS artifact that still requires PBS lookups to be useful.

### Q1.5 Traceability Impact of Moving to FBS (FR-1.4)

If 05-operation were moved to FBS:

| Impact | Assessment |
|---|---|
| Files referencing `cross-cutting/05-operation/` that need path updates | 17 files across product-breakdown/ (README.md, product-tree.md, breakdown-structures.md, traceability-map.md, gap-analysis.md, candidates/IMP-021.md, etc.) |
| FBS artifacts that currently have no path references | Would need new path references, potentially violating G-01 |
| PBS traceability | `gap-analysis.md` line 85 maps `cross-cutting/05-operation/` to "All functions (satisfies non-functional requirements)" — this mapping would need restructuring |
| WBS traceability | `wbs.md` WP-17 traces to "PBS: 05-operation/ layer" — would need reclassification |
| IMP-021 candidate | References creating `cross-cutting/05-operation/verification.md` — would need updating |
| Decision records | ED-001 and associated decisions reference cross-cutting evolution path |
| Navigation impact | Users looking for operational requirements in `cross-cutting/05-operation/` would find nothing; need to remember they moved to FBS |

**Blast radius estimate:** 15–20 files, comparable to IMP-017 (40+ files). Slightly smaller because only one layer moves, not the entire directory structure.

### Q1.6 Recommendation (FR-1.5)

**Do not move 05-operation to FBS as-is. Do not reframe for FBS placement.** The content is PBS-nature (operational procedures, deployment constraints) and would violate architecture guardrail G-01 if moved. INCOSE guidance supports operational functions in FBS, but the current content describes operational *procedures* and *deployment mechanism*, not operational *functions*. The cost-benefit is negative: high reframing effort + loss of precision + 15–20 file updates for a classification that stretches FBS semantics.

**Alternative recommendation:** Keep 05-operation in cross-cutting but strengthen its labeling. Add a section to the layer README explicitly stating: "This layer captures operational and deployment requirements that respond to functional needs (FBS) for availability, reliability, and maintainability while describing physical operation procedures (PBS)."

### Q2.3 INCOSE/SE Best Practices (FR-2.2)

INCOSE §2.3.4.1 and MIL-STD-881 state:
- WBS decomposes the work activities required to realize the system.
- Improvement/sustaining engineering is a legitimate WBS category (MIL-STD-881 Section H: Sustaining Engineering and Support).
- Evolution/improvement lifecycle management maps to WBS under sustaining engineering.

**Researcher finding (INCOSE/MIL-STD-881):** Evolution/improvement belongs in WBS under Systems Engineering / Sustaining Engineering.
**Architecture assessment:** 06-evolution is a split case — `wbs.md` is pure WBS content; candidates/selected/done directory is product structure (PBS-nature).
**Lessons (KM-004):** Minimize parallel structures — supports removing cross-cutting contents into proper decomposition slots.

**Tension resolution:** The INCOSE principle applies cleanly to `wbs.md` and partially to `roadmap.md` and `risks.md`. However, the remaining 06-evolution artifacts describe *the product structure of the evolution layer itself* — where candidates live, how they transition to selected/done, what decisions govern them. These are PBS artifacts about how the product-breakdown is managed. Moving only the WBS-nature parts to a separate WBS structure would split the co-located set of evolution artifacts across two locations, violating KM-004 (minimize parallel structures).

### Q2.4 Partial vs Full WBS Incorporation Feasibility (FR-2.3)

**Option A — Full move (all 06-evolution to WBS):** Not feasible. Candidates, selected, done, decisions, README, changelog, and gap-analysis are PBS-nature. Moving them to a WBS directory would create an even worse classification mismatch than the current cross-cutting placement.

**Option B — Partial move (wbs.md + roadmap.md + risks.md to WBS):** Feasible but costly:
- Would create a separate WBS directory (e.g., `product-breakdown/wbs/`) with 3 files.
- Would leave candidates/selected/done/decisions/README/changelog/gap-analysis in cross-cutting or need to move them to PBS.
- Would split the evolution layer across two locations, degrading navigability (violates KM-006).
- Would require updating all references to the moved files across 60+ references (06-evolution references are widespread).
- `wbs.md` current traceability already maps each work package to its FBS/PBS origin — this mapping is valid regardless of directory location.

**Option C — Create independent WBS structure:** Possible as a future improvement, moving `wbs.md` content into a separate WBS breakdown and adding a dedicated `wbs/` directory. This would be the architecturally cleanest approach for `wbs.md` but leaves the rest of 06-evolution untouched.

**Blast radius estimate:** 60+ files for full move, 15–25 files for partial move. Higher than IMP-017 (40+ files) for full move.

### Q2.6 Recommendation (FR-2.5)

**Do not move 06-evolution to WBS at this time.** The content is a mixed set where only `wbs.md` (and partially `roadmap.md`, `risks.md`) is WBS-nature. Creating a split across two locations degrades the single authoritative location for evolution artifacts that is easy to navigate and maintain.

**Alternative recommendation:** Keep 06-evolution in cross-cutting. The current `wbs.md` already contains a correct WBS mapping (each work package traces to its FBS or PBS origin). The location is pragmatic — co-located with the improvement lifecycle it plans. If a separate formal WBS structure is desired in the future, create `product-breakdown/wbs/` as a new top-level grouping (not as a move from 06-evolution) that includes `wbs.md` content and potentially additional planning artifacts, while keeping 06-evolution as the improvement lifecycle layer.

## Question 3: Better Utilization of FBS/PBS/WBS Separation

### Q3.1 Current Boundary Assessment (FR-3.1)

The current decomposition model has clearly defined boundaries:

| Boundary | Documented In | Quality |
|---|---|---|
| FBS vs PBS | `breakdown-structures.md` Boundary table (lines 235-248) | **Well-defined.** Explicit table assigns each artifact to FBS, PBS, or cross-cutting with rationale. |

### Q3.2 Boundary Violations Found (FR-3.2)

After reviewing all decomposition artifacts, the following boundary issues were identified:

| Severity | Location | Issue | Rationale |

| **Low** | `breakdown-structures.md` boundaries table (line 253) | Lists cross-cutting layers under PBS boundary rule (#2) as "PBS artifacts" | Creates ambiguity: cross-cutting layers are listed as PBS artifacts in rule #2 but also documented as spanning both FBS and PBS. ### Q3.3 Improvement Opportunities (FR-3.3)

1. **Strengthen cross-cutting labeling:** Update `breakdown-structures.md` boundary rule #2 to explicitly say "PBS artifacts and cross-cutting layers (which are PBS-nature but span FBS) describe how the system is physically structured." This removes the ambiguity between "PBS artifacts" and "cross-cutting artifacts."

2. **Add cross-cutting origin annotations:** In `cross-cutting/README.md`, add explicit "Derives from FBS" annotations for each cross-cutting layer (e.g., "05-operation: derives from user needs for availability, reliability, maintainability — reflected in PC-001 through PC-010"). 3. **Create a WBS root-level directory:** Consider creating `product-breakdown/wbs/` as an optional future improvement, housing `wbs.md` and planning artifacts (roadmap, risks) while keeping improvement lifecycle artifacts in cross-cutting/06-evolution. This would satisfy INCOSE MECE alignment for WBS without disrupting the evolution layer.

4. **Per-layer boundary adherence self-checks:** Add a small checklist to each layer README:
   - FBS layers: "No file paths, agent names, or physical structure references"
   - PBS layers: "Traces to FBS function, does not duplicate functional description"
   - Cross-cutting layers: "Documents which FBS functions and PBS components this spans"

### Q3.4 Benefit vs Disruption Assessment (FR-3.4)

| Improvement | Benefit | Disruption | Net Assessment |
|---|---|---|---|
| Strengthen cross-cutting labeling | Low ambiguity reduction, minimal | Zero (documentation only) | **Positive — implement in documentation update** |

### Q3.5 Recommendations (FR-3.5)

1. **Immediate (documentation):** Update `breakdown-structures.md` boundary rule #2 to clarify cross-cutting layer classification. Add cross-cutting origin annotations to `cross-cutting/README.md`. Add per-layer boundary adherence checklists to layer READMEs. (Effort: < 1 hour for an agent, 2–3 files changed.)

(Effort: low-medium, but requires coordination with cross-cutting/06-evolution to avoid duplication.)

3. **Not recommended at this time:** Any restructuring that moves cross-cutting content into FBS or PBS directories. The current boundary is well-maintained and the classification is reasonable.

### Q4.4 Evaluation Against KM-004 and KM-006 (FR-4.4)

**KM-004 (Minimize parallel structures):**
- *Supports removal:* If cross-cutting content is cleanly assigned to FBS/PBS/WBS, there is no parallel structure — every artifact has one canonical location. This is the ideal INCOSE outcome.
- *Counters removal:* The mixed nature of cross-cutting artifacts (Q4.2) means that after "removal," the residual cross-cutting artifacts would need either a new grouping or parallel placement in both FBS and PBS. Creating a different grouping for residual artifacts still violates KM-004 — it just changes the group name.
- *Net:* KM-004 weakly supports removal for cleanly classifiable artifacts but does not support removal for inherently cross-cutting artifacts.

**KM-006 (Hierarchical layout):**
- *Supports removal:* None. The current 3-group layout (fbs/, pbs/, cross-cutting/) is easy to scan. Removing cross-cutting creates 4+ top-level groups or a flat structure, increasing cognitive load.
- *Counters removal:* After removing cross-cutting, the top-level directories would be: fbs/, pbs/, and potentially wbs/, plus 2-4 root-level cross-cutting files (breakdown-structures.md, traceability-map.md, decision-log.md). This adds navigational complexity and breaks the clean 3-group pattern.
- *Net:* KM-006 strongly counts against removal — the hierarchical layout degrades.

### Q4.5 Recommendation (FR-4.5)

**Do not remove cross-cutting at this time.** The evaluation yields the following balance:

**Arguments against removal:**
1. **Residual cross-cutting content:** 20-30% of cross-cutting artifacts (breakdown-structures.md, traceability-map.md, decision-log.md, gap-analysis.md, acceptance-criteria strategy, ED-001) are inherently cross-cutting and cannot be cleanly redistributed.
2. **Blast radius:** 50-70 affected files, exceeding IMP-017 precedent. Risk of stale references (KM-007) and orphaned nodes (KM-008) is high.
3. **Navigation degradation:** The clean 3-group layout (KM-006) would become a messier 4+ group flat layout plus root-level orphans.
4. **Recent restructuring:** IMP-017 was completed on 2026-06-29. Restructuring again immediately risks structural churn and agent confusion.
5. **Architecture assessment:** Architecture guardrails confirm cross-cutting serves a real transversal purpose. The architecture does not recommend removing cross-cutting.

**Arguments for removal (acknowledged):**
1. **INCOSE MECE alignment:** A strict interpretation of INCOSE/ISO 15288 prefers every artifact in exactly one decomposition type.
2. **KM-004 (minimize parallel):** Removing cross-cutting eliminates the parallel grouping.
3. **Simplicity:** Fewer structural categories to explain to new contributors.

**Resolution:** The tension between INCOSE purity and practical architecture is resolved in favor of **pragmatic architecture with strengthened documentation**. The cross-cutting grouping is retained but its rationale is better documented. The residual cross-cutting artifacts (breakdown-structures.md, traceability-map.md, decision-log.md) are explicitly acknowledged as "structural cross-cutting" — root-level artifacts that define the relationship between FBS, PBS, and WBS rather than belonging to any one.

**Deferred improvement:** If future work creates a dedicated `product-breakdown/wbs/` directory (as recommended in Q2.6), the remaining cross-cutting contents (04-verification, 05-operation, 06-evolution minus wbs.md/roadmap/risks) would shrink to a more manageable scope. At that point, the question of whether cross-cutting should be "verification + operation + evolution lifecycle" or redistributed can be revisited with lower blast radius.
