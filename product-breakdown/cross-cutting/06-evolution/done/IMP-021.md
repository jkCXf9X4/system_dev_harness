## Theme

Verification / INCOSE Alignment — Evolve the verification artifact pattern from centralized-only to a dual INCOSE pattern (centralized strategy + per-element horizontal-view criteria)

## Source Evidence

- INCOSE SE Handbook v5.1 **§1.3.5** (The Hierarchy within a System): The horizontal view at each architecture level "includes requirements; integration, verification, or validation activities and results." Verification criteria belong with the element they verify — they are part of that element's horizontal view.
- INCOSE SE Handbook v5.1 **§2.3.5.9** (Verification Process): "The planning of the verification is done recursively at each lower level as the definition of the system or a system element evolves." Verification actions occur "recursively for each layer." Each level has its own verification criteria, method, and success criteria.
- INCOSE SE Handbook v5.1 **§2.3.4.1** (Breakdown Structures): The PBS is "a breakdown of the SoI into successively lower-level details of its physical architecture." The handbook does NOT prescribe a separate "verification" branch in the PBS — verification is a horizontal concern of each PBS element, not a standalone physical product.
- IMP-013: Pilot horizontal-view artifact at `pbs/02-architecture/verification.md` established the per-layer pattern.

## Current Pain Or Risk

The current approach has a centralized `cross-cutting/04-verification/acceptance-criteria.md` described as the "authoritative source" alongside a pilot per-layer artifact (`pbs/02-architecture/verification.md`) described as a "pilot horizontal view." This creates authority ambiguity and does not fully resolve the dual-ownership tension between centralized and per-element criteria. The following layers lack local verification artifacts entirely: `fbs/00-intent/`, `fbs/01-product/`, `pbs/03-implementation/`, `cross-cutting/05-operation/`, `cross-cutting/06-evolution/`.

## Proposed Improvement

Complete the per-layer verification artifact pattern for all PBS/FBS layers, following the INCOSE dual pattern: (1) centralized verification strategy document (repurposed from current `acceptance-criteria.md`) defines the overall approach, methods, and cross-cutting concerns; (2) per-layer `verification.md` artifacts in each PBS/FBS element directory contain the element-specific acceptance criteria and verification gates.

## Expected Benefit

Full INCOSE alignment — verification criteria co-located with the element they verify per §1.3.5 horizontal view and §2.3.5.9 per-level recursion. Authority ambiguity resolved (centralized = strategy, per-layer = authoritative for element). Stronger traceability — changes to an element's requirements, architecture, or implementation are visibly adjacent to its verification criteria.

## Risk And Blast Radius

Medium — requires creating 5 new verification.md files across fbs/00-intent, fbs/01-product, pbs/03-implementation, cross-cutting/05-operation, cross-cutting/06-evolution. Requires refactoring the centralized acceptance-criteria.md from authoritative source to strategy overview + index. Must coordinate with existing traceability-map.md and breakdown-structures.md. Risk of cross-cutting consistency if per-layer files diverge — mitigation: centralized strategy defines cross-cutting concerns each layer must address.
